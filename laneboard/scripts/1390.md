# Hand test #1390 (CUSTOMER-CODE-IDENTITY)

## URL
crew test copy

## Setup

1. Sign in as an admin (someone who can open Order Management > Customers and Supply Chain > Sales Orders).
2. The test copy must have run migration `cci_0001_customer_code_identity` on its database (the merge is the destructive half crew holds; the crew-migration comment on the PR carries the SQL). Before it runs, the Customers page shows 300-1001 three times; after it, once.
3. Have the external API key for the test copy at hand (the `EXTERNAL_API_KEY` of the backend `.env`), and the company code of Sorento (`companyCode` in the ingest payloads below, the same value the ESB sends).
4. Note the `id` of the surviving 300-1001 customer from its detail page URL.

## Steps

1. From the sidebar open Order Management > Customers and search `300-1001`. Count the rows.
2. Open the 300-1001 row. Read the line under "Customer Code" in the header.
3. Search `300-4002` and `300-H030` on the Customers page. Count the rows for each.
4. Push a sales order for 300-1001 under a changed debtor name (replace `<companyCode>` and the key):
   ```
   curl -s -X POST http://<test copy backend>/api/v1/external/ingest/sales_orders \
     -H "X-API-Key: <EXTERNAL_API_KEY>" -H "Content-Type: application/json" \
     -d '{"companyCode":"<companyCode>","records":[{"source_ref":"HT1390-SO-1","so_number":"HT1390-SO-1","status":"open","customer_code":"300-1001","customer_name":"MODERNMED SDN BHD","lines":[{"source_ref":"HT1390-SOL-1","product_code":"<any live product code>","qty_ordered":2}]}]}'
   ```
   Read the `records[0].warnings` and `records[0].entity_id` in the reply.
5. From the sidebar open Supply Chain > Sales Orders and search `HT1390-SO-1`. Read the Customer column. Open the order and read the customer name on the detail.
6. Back on Order Management > Customers, search `300-1001` again. Count the rows and open the row; read the customer name and the "Also known as" line.
7. Push the same order again with `"customer_name":"1 LIVING DEPOT SDN BHD"` (same `source_ref`). Search `HT1390-SO-1` on Supply Chain > Sales Orders and read the Customer column.
8. Push a sales order with a brand-new code: `"customer_code":"300-HT1390","customer_name":"HANDTEST FIRST SDN BHD"`, `source_ref` `HT1390-SO-2`. Then push another with `"customer_code":"300-HT1390","customer_name":"HANDTEST SECOND SDN BHD"`, `source_ref` `HT1390-SO-3`. Search `300-HT1390` on the Customers page.
9. On Order Management > Customers press Add, enter code `300-1001` and name `ANYTHING NEW`, save.
10. Open `GET http://<test copy backend>/api/v1/external/contract` with the API key and search the `warnings` list for `customer_ambiguous`.

## Expected

1. Exactly one row for 300-1001 (before the migration ran: three).
2. "Also known as: 1 LIVING DEPOT SDN BHD [A/C I], MODERNMED SDN BHD" (the two merged-away names; the order may differ by which row was oldest). The surviving row's own name is unchanged.
3. Exactly one row each for 300-4002 and 300-H030.
4. `warnings` does NOT contain `customer_created`; `entity_id` is a new sales order id. No error.
5. The Customer column and the detail both read `MODERNMED SDN BHD` (the name the order was issued under), not the master name.
6. Still exactly one row for 300-1001. Its name is unchanged and "Also known as" is unchanged: a document never renames or aliases the master.
7. The Customer column now reads `1 LIVING DEPOT SDN BHD`: the order carries its own latest name.
8. Exactly one row `300-HT1390` named `HANDTEST FIRST SDN BHD`; the second push landed on it (its reply carries no `customer_created`). On Supply Chain > Sales Orders `HT1390-SO-2` shows `HANDTEST FIRST SDN BHD` and `HT1390-SO-3` shows `HANDTEST SECOND SDN BHD`.
9. The save is refused with "Customer with this code already exists." and no second 300-1001 row appears.
10. `customer_ambiguous` is listed.
