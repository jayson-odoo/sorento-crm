# PR 2368 hand test: chatbot replies faster, same answers (CHATBOT-SPEED)

What the owner sees: the same 7 questions asked twice in the Chatbot Console, once on today's main code ("old") and
once on this PR ("new"), with each reply's time side by side and the answers unchanged. No screen changes in this PR;
only the time goes down.

## URL
crew test copy

## Setup
- One crew test copy and one database for both runs, so only the code differs:
  - **Run A (old):** the copy's backend on main at `4dfe5b2f` (this PR's base). After the switch, uvicorn `--reload` restarts it.
  - **Run B (new):** the copy's backend on this PR's head (`git checkout <PR head>`; the head is in the latest crew-status on PR 2368).
  - The frontend can stay on the PR head for both runs; this PR changes no frontend file.
- The worker is not needed: Console turns run in the API process.
- The copy's AI settings as they are (the parser model and the span step on, as in prod). No setting is changed.
- Sign in as admin. In the Console's **Contact** picker choose one **staff** contact and keep it for both runs. A staff contact loads the most lookup rows (customers, suppliers, salespeople), which is the slow part this PR speeds up.
- Pace: send each question as soon as the previous reply has arrived, as a real chat does; open the traces only after the last question. A pause of more than 30 s between questions lets the kept-open connection close and adds back one handshake.
- Spend: about 16 turns x 2 model calls (parser + span) = 32 calls on the copy's own key, inferred US$0.10-0.35 in total. Log the real figure in the PR 2368 ledger.

## Steps
1. Run A: with the backend on `4dfe5b2f`, from `/` open System Management > Chatbot Console in the sidebar.
2. Choose the staff contact in Contact. Send `hi` and wait for the reply. This is a warm-up after the restart and is not counted.
3. Send these 7 questions one after another, each as soon as the previous reply arrives:
   1. `stock SRTWC8517`
   2. `any basin 600mm in stock?`
   3. `please share new mocha promotion`
   4. `srt a3 flyer`
   5. `matt black tap price`
   6. `hi, ada stok sinki double bowl?`
   7. `who supplies kitchen sinks?`
4. Under each of the 7 replies, click **trace**. Note three numbers per question: the turn time in the drawer header, the **Understood** stage time, and the **Span pass** time. Press Escape to close each drawer.
5. Run B: crew switches the copy's backend to the PR head (the page can stay open). Reload the Console page and choose the same staff contact again.
6. Repeat step 2 (warm-up `hi`) and step 3 (the same 7 questions, in the same order, at the same pace).
7. Repeat step 4 for the 7 new replies.
8. Crew prints the side-by-side table from the stored turns (read-only, no model call). From `sorento_crm_backend/` on the copy's head:
   `SORENTO_ENV_FILE=<copy env> venv/bin/python -m scripts.chatbot_eval.speed_table --minutes 120`
   and pastes the table into the hand-test thread.
9. Put each old reply next to its new reply (the Console threads, or the table's last column).

## Expected
- Step 3 and step 6: every question gets a reply; nothing hangs and nothing errors.
- Step 4 vs step 7: on each question, Run B's **Understood** time is lower than Run A's. Run B's turn time is lower too, on most questions.
- The drawer looks the same in both runs. The new turns also store two extra timings (row loading, matching), which the drawer does not show; the table in step 8 uses them to tell old turns from new ones.
- Step 8: the table looks like this. The numbers are inferred from prod's 11 Nov medians; the copy's own numbers replace them.

|---|---|---|---|---|---|---|
| stock SRTWC8517 | about 2.1 | about 1.3-1.7 | about 0.4-0.8 | about 7.6 | about 6.8-7.2 | yes |
| (each of the 7 questions) | ... | ... | ... | ... | ... | yes |
| **Median** | about 2.1 | about 1.3-1.7 | **about 0.4-0.8** | about 7.6 | **about 6.8-7.2** | |

- "Before the parser" is the Understood stage minus the parser's own model call. It is the part this PR speeds up, and it should drop on **every** question. The whole-turn column also carries the parser's run-to-run noise (about +/- 0.5 s), so one question can come out even. The median row shows the gain.
- Step 9: the same answer on all 7 questions (same products, codes, quantities, wording), so "Same answer" reads yes on every row. If one row reads NO, crew re-asks that question once on each run. A model-worded difference that comes back the same on the re-ask is model noise, not this PR (the PR changes no input to any model call). A difference that repeats is a defect: report it on PR 2368.
- Not visible here: the respond.io check that runs before every real WhatsApp turn also gets faster (inferred 0.1-0.3 s), but the Console does not make that check. It shows after release, on real turns, in each turn's `inbox` timing (`lookup_ms`).
