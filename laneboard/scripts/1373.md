# Hand test: PR #1373 PO-SPO-WAREHOUSE (chatbot SPO routing, warehouse filter, sort)

## URL

crew test copy

## Setup

1. Publish the new parser prompt on the test copy's database (crew's migrate step does not
   run alembic data migrations): from `sorento_crm_backend/` with the test copy's env,
   run `venv/bin/python -m scripts.publish_parser_prompt`. It prints
   `published chatbot_semantic_parser v<N>` (or `already published as v<N>`).
2. Open the Chatbot Console, prompt version picker for `chatbot_semantic_parser`, and
   select that version `<N>` (the highest version number; the `production` label is not
   moved by the script).
3. Use a staff contact (the console's default test contact 437264483 is fine). No field
   reveal is needed for a direct PO or SPO ask; `purchase_orders.supplier` only decides
   whether the Supplier line shows.
4. Make sure BRW and BRW-BB exist as warehouse codes and SRT79-SS / SRTWC286 have open PO
   lines and SPO lines on the copy (the prod copy has both). If a code has none, swap it
   for one that does; a "no PO" / "no SPO line" miss on an empty code is correct.

## Steps

1. Type `PO to BRW`.
2. Type `SPO for BRW-BB`.
3. Type `SPO SRT79-SS`.
4. Type `last in SRTWC286 at BRW`.
5. Type `latest PO for SRT79-SS`.
6. Type `oldest first` (nothing else).
7. Type `SPO biggest quantity first at BRW`.
8. Type `stock for SRTWC286` (a different ask, to confirm the sort does not leak).
9. Optional: run `venv/bin/python scripts/chatbot_console_check.py tests/chatbot/console_cases/2026-09-29-po-spo-warehouse.yaml --base-url http://127.0.0.1:8000 --sleep-seconds 8` for the same turns graded automatically (row ORDER is graded by eye).

## Expected

1. A "PO placed" list. Every row's `Location` is `BRW`. The trace's parse stage shows
   `domain_hint: purchase_order`, an entity `BRW` with hint `warehouse`, and the fetch
   args carry `warehouse_ids` with one uuid.
2. An SPO line answer ("Here is the last SPO line per product."): the newest SPO line at
   BRW-BB (one row, the tool's unscoped default, owner ruling "keep it as it is"), its
   `Warehouse` is `BRW-BB`. NOT an incoming / ETA answer. Parse stage:
   `domain_hint: spo_allocation`, `intent_hint: check_spo`, entity `BRW-BB` hinted
   `warehouse`. Fetch args: `warehouse_ids`, no `top_n`. Typing `last 3 SPO for BRW-BB`
   afterwards gives three rows (`top_n: 3`).
3. The SPO line(s) for `SRT79-SS` (one row per product of the family), never an
   incoming answer. Parse stage: `domain_hint: spo_allocation`, entity SRT79-SS hinted
   `product`.
4. Unchanged from before this PR: one row per SRTWC286 product at BRW (`Warehouse: BRW`).
5. PO placed rows for SRT79-SS with the NEWEST `PO Date` first. Parse stage:
   `sort_by: date`, `sort_dir: desc`; fetch args `sort: po_date`, `dir: desc`.
6. The same PO rows re-listed OLDEST `PO Date` first, no question asked, no domain change.
   Parse stage: `domain_hint` null, entities [], `sort_by: date`, `sort_dir: asc`; fetch
   args `sort: po_date`, `dir: asc`.
7. The SPO line at BRW with the LARGEST `SPO Quantity` (one row, the unscoped default;
   "top 5 SPO biggest quantity first at BRW" would give five). Fetch args:
   `warehouse_ids`, `sort: spo_quantity`, `dir: desc`, no `top_n`.
8. A normal stock answer for SRTWC286; its fetch args carry no `sort` / `dir` (the new ask
   dropped the carried sort).
