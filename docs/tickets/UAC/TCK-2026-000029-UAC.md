# UAC — TCK-2026-000029 — WhatsApp on escalation + assignment

Spec: [../TCK-2026-000029.md](../TCK-2026-000029.md). Worker on `respond_io` queue required for send criteria. See [protocol](./README.md).

## Functional

- [ ] **AC-29-F1 [F] — WhatsApp on escalation when opted in.**
  Given an escalation (auto or manual) whose resolved assignee has `notify_whatsapp=True` + a linked RespondContact,
  When the notification is created,
  Then a `whatsapp` `NotificationDelivery` row is created and a `respond_io` send is enqueued for that user's `respond_io_id`.
  **Validate:** `pytest tests/test_whatsapp_notifications.py::test_escalation_creates_whatsapp_delivery`; integration smoke: escalate → `psql -c "select channel from notification_deliveries order by created_at desc limit 3;"` includes `whatsapp`.

- [ ] **AC-29-F2 [F] — WhatsApp on new assignment.**
  New assignment to such a user → WhatsApp fires (same gating).
  **Validate:** `pytest tests/test_whatsapp_notifications.py::test_assignment_creates_whatsapp_delivery`

- [ ] **AC-29-F3 [F] — No WhatsApp on other events.**
  Response, resolution, reminder notifications → **no** `whatsapp` delivery row.
  **Validate:** `pytest tests/test_whatsapp_notifications.py::test_no_whatsapp_for_response_resolution_reminder`

- [ ] **AC-29-F4 [F] — 24h-window text vs template.**
  Window open → `sent_as='text'`; window closed → `sent_as='template'` using the registered use-case template (`sla_escalation` / `sla_assignment`).
  **Validate:** `pytest tests/test_whatsapp_notifications.py::test_window_open_text_closed_template` (mock `get_window_state`).

- [ ] **AC-29-F5 [F] — Gating skip is graceful.**
  Recipient with `notify_whatsapp=False` OR no linked contact → no `whatsapp` delivery; `in_app` + `email` deliveries still created.
  **Validate:** `pytest tests/test_whatsapp_notifications.py::test_skip_when_optout_or_no_contact`

- [ ] **AC-29-F6 [F] — No CRM-side ack (negative).**
  No ack endpoint, ack page, or `acknowledged_at`/`acknowledged_by` columns exist. The OK is template-side only.
  **Validate:** `curl -i .../api/v1/sla/escalations/x/ack` → 404; `psql -c "\\d conversation_sla_event_logs"` has no `acknowledged_*` columns.

## Business

- [ ] **AC-29-B1 [B] — Management receives escalation on WhatsApp.**
  A director user (tier-3, `notify_whatsapp` on, linked contact) receives a WhatsApp when an escalation reaches their tier and they are the picked assignee.
  **Validate:** seed a tier-3 director, escalate to tier 3 → assert a `whatsapp` delivery + queued send addressed to their `respond_io_id`. `pytest tests/test_whatsapp_notifications.py::test_director_receives_on_tier3`

## Data

- [ ] **AC-29-D1 [D] — whatsapp channel supported.**
  `NotificationDelivery.channel='whatsapp'` is accepted/persisted.
  **Validate:** insert + read back in a test; no constraint violation.

## Scalability

- [ ] **AC-29-S1 [S] — Async send (XS1).**
  The notification-creating request returns promptly; the WhatsApp send executes on the worker, not in-request.
  **Validate:** `pytest` asserts the create path enqueues (does not call Respond synchronously); request latency criterion in integration smoke.

- [ ] **AC-29-S2 [S] — Send failure is best-effort (XS3).**
  A Respond send failure marks the `whatsapp` delivery `failed` + logs it; the originating escalation/assignment still succeeds; other channel deliveries unaffected.
  **Validate:** `pytest tests/test_whatsapp_notifications.py::test_send_failure_does_not_break_escalation` (mock Respond to raise).
