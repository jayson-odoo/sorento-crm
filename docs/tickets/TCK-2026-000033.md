# TCK-2026-000033 — PWA: installable + web-push notifications

> **Source:** directors' session 2026-06-17. "Enable PWA" + "PWA for Sorento AI normal users to get notifications." Grilled 2026-06-17.
> **Priority:** high · **Category:** feature
> **Dependencies:** none. Lights up the existing unused `web_push` delivery channel.

## Goal

Make the Next.js frontend an **installable** PWA and deliver **web-push notifications**, so users get alerts without the app open. The notification backend already models a `web_push` channel — wire it end to end.

## Design decisions (from grilling)

- **Scope: install + web push, minimal offline.** Manifest + icons (installable / Add-to-Home-Screen) + a service worker that handles `push` and `notificationclick`. **No** offline app-shell/asset caching beyond what installability requires. **Never cache `/api/v1/*`** (auth + freshness). Avoids cache-invalidation complexity against the no-HMR prod-build model.
- **Push scope = mirror in-app; subscription is the opt-in.** Any notification that creates an `in_app` delivery also creates a `web_push` delivery for users with an **active push subscription**. The browser-permission subscription IS the opt-in — **no separate pref column**. Unsubscribe = revoke in browser / toggle in UI. Consistent with the notification center (no per-type filtering, no extra toggle).
- **iOS:** web push requires the app be **added to home screen** (A2HS) and **iOS 16.4+**. Document this; installability is mandatory (hence not "push-only").

## Background (verified)

- No PWA today: no `public/manifest`, no service worker, no `next-pwa`/`workbox`; `next.config.mjs` has only `output: 'standalone'`.
- `NotificationDelivery` already supports a `web_push` channel (created by `NotificationService`, never delivered). In-app center: `app/components/partials/topbar/notifications-sheet.tsx` + `services/notificationService.ts`.
- Prod build via `npm run build && npm start`, no HMR; `NEXT_PUBLIC_BASE_PATH` in play — manifest `start_url` + SW scope must honour the base path.

## Files to change

### Frontend

- `public/manifest.webmanifest`: name/short_name, icons 192/512 + maskable, `display: standalone`, `start_url` (base-path aware), theme/background color. Add `<link rel="manifest">` in the root layout.
- App icons in `public/` (from the brand asset).
- Service worker: `@ducanh2912/next-pwa` (or hand-rolled SW registered from a client component). Must (a) satisfy installability, (b) handle `push` (show notification) + `notificationclick` (focus/open the deep link). **No `/api/v1/*` caching.** SW scope respects base path.
- `services/pushService.ts`: on permission grant `pushManager.subscribe({ applicationServerKey: VAPID_PUBLIC })`, POST to backend; unsubscribe DELETEs. An "Enable notifications" control in account settings / the notifications sheet.

### Backend

- Migration: `web_push_subscriptions` (user_id, endpoint, p256dh, auth, ua, created_at).
- Endpoints: `POST/DELETE /api/v1/notifications/push/subscriptions`.
- VAPID via env (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`); public key to FE via `NEXT_PUBLIC_VAPID_PUBLIC_KEY`.
- `app/tasks/notification_tasks.py` (`send_notification_deliveries`): implement the `web_push` branch — for each of the user's subscriptions send via `pywebpush`; on 404/410 prune the dead subscription; mark delivery `sent`/`failed` like the email path.
- `NotificationService`: ensure a `web_push` delivery is created whenever `in_app` is (for users with ≥1 subscription) — mirrors in-app.
- `requirements.txt`: add `pywebpush`.

## Acceptance

- Installable (Chrome/Edge "Install app"; Android A2HS); Lighthouse installability checks pass.
- Static shell loads when offline; `/api/v1/*` still requires network (not served stale).
- Granting permission creates a subscription row; a new in-app notification also produces an OS push; clicking it opens the deep link.
- Unsubscribe removes the row; expired endpoints pruned on send (404/410).
- `start_url` + SW scope honour `NEXT_PUBLIC_BASE_PATH`.
- iOS 16.4+ after A2HS receives push (documented manual check).

## Rollback

Unregister + delete the SW and manifest link; drop `web_push_subscriptions` + the push endpoints; leave the `web_push` delivery branch a no-op. In-app + email unaffected.
