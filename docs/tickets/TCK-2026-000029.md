# TCK-2026-000029 — SLA notifications via WhatsApp (escalation + assignment)

> **Source:** directors' session 2026-06-17. "Escalation notification via WhatsApp" + "WhatsApp update to CK, put an OK button". Grilled 2026-06-17.
> **Priority:** high · **Category:** feature
> **Dependencies:** TCK-2026-000031 (per-user phone + user↔RespondContact link + `notify_whatsapp` toggle). Shares the escalation event with TCK-2026-000028.

## Goal

Add **WhatsApp** as a notification delivery channel. When an SLA row **escalates** (auto-scan or manual, TCK-28) **or is newly assigned** to a user, that user also gets a WhatsApp message — **if** they have `notify_whatsapp` on and a linked RespondContact. In-app + email are unchanged.

## Design decisions (from grilling)

- **Trigger scope:** WhatsApp fires on **escalation** events (auto + manual) **and new assignment** events only. Response, resolution, and reminder notifications stay in-app + email (no WhatsApp).
- **Recipient:** the **single** resolved assignee (round-robin `get_next_assignee` owner at the target tier / the newly-assigned user). No team broadcast, no fixed management-trio CC — directors are tier-3 assignees, so they receive it when escalation reaches their tier and they're the picked owner.
- **Gating:** send only if the recipient user has `notify_whatsapp=True` (TCK-31) **and** a resolvable RespondContact (`respond_io_id`). Otherwise skip WhatsApp silently; other channels still fire.
- **24h window:** reuse `respond_messaging_service.send_text_or_template()` — window open → plain text; window closed → the approved template for the use-case.
- **The "OK":** when a **template** is sent (out-of-window), the approved WhatsApp template carries a **quick-reply OK button**. That button is **defined in Meta/Respond.io, not built by our code**, and the tap is a **WhatsApp-side affordance only** — the CRM does **NOT** capture or record it. When a plain text is sent (in-window) there is no OK button (recipient is already in conversation).
- **Therefore dropped vs the original draft:** no ack endpoint, no ack landing page, no `acknowledged_at`/`acknowledged_by` columns, no token minting. WhatsApp here is pure outbound notification.

## Background (verified)

- Outbound send: `app/services/respond_messaging_service.py:send_text_or_template()` (`:265`), `send_template_for_use_case()` (`:212`); window via `get_window_state()`. Sends are queued on the `respond_io` RQ queue (`app/tasks/respond_io_tasks.py`).
- Notifications: `NotificationService.create_with_channel_preferences(...)` builds `NotificationDelivery` rows per channel (`in_app`/`email`/`web_push`); async send via `notification_tasks.send_notification_deliveries`.
- The send path passes **body params only** — it does not construct interactive/URL buttons. That's fine: the quick-reply lives in the pre-approved template, so no button-param work is needed.

## Files to change

### Backend

- `app/models/notification.py`: allow `channel='whatsapp'` on `NotificationDelivery` (free-text column → no migration; if checked, extend the constraint).
- `app/services/notification_service.py` (`create_with_channel_preferences`): for **escalation** and **assignment** notification types, when the target user has `notify_whatsapp=True` **and** `resolve_user_respond_io_id(user)` (TCK-31) returns an id, add a `whatsapp` delivery row. Other notification types never create a `whatsapp` delivery.
- `app/tasks/notification_tasks.py` (`send_notification_deliveries`): implement the `whatsapp` branch — resolve `respond_io_id`, call `send_text_or_template(...)` with use-case `sla_escalation` / `sla_assignment` (register both in `respond_template_defaults`; each approved template includes the quick-reply OK). Template params: entity number, form type, tier, due (KL wall-clock), deep link. Mark delivery `sent`/`failed`, attach `request_payload` to the integration log.
- Templates: register the two use-cases + their param mappings; document that the approved template's quick-reply button is owned in Meta/Respond, not here.

### Frontend

- None required for sending. (The recipient-side toggle + contact link UI is TCK-31.) Optionally surface a "WhatsApp sent" indicator on the SLA event row from the `whatsapp` delivery status — nice-to-have, not required.

## Acceptance

- Escalating a complaint (auto or manual) to a tier whose picked assignee has `notify_whatsapp` on + a linked contact → a WhatsApp send is queued (verify integration log). Window open → text; window closed → template (with its quick-reply OK).
- Newly assigning a row to such a user → WhatsApp fires.
- Response / resolution / reminder events → **no** WhatsApp.
- Recipient with `notify_whatsapp` off OR no linked contact → no WhatsApp; in-app + email still fire.
- No ack rows/columns/endpoints exist — the OK is WhatsApp-side only.
