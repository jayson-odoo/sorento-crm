# TCK-2026-000017 — `crm_incoming_stock_by_product`: embedding pre-resolve + ilike

> **Source ticket:** `TCK-2026-000017` (status: draft)
> **Priority:** medium · **Category:** feature
> **Dependencies:** product embedding already exists (`embedding_worker.py` lines 73–83). No upstream ticket required.

## Goal

User asks for `WC101` but the system has `SRTWC101` and `SRTWC101-RL`. Today the tool exact-matches — misses. Switch to: **embedding pre-resolve → expanded candidate codes → ilike on product_code/product_name/product_description**, returning matched candidates for transparency.

Apply same shape to every MCP tool that filters by product:
- `crm_incoming_stock_by_product` (primary scope)
- `crm_incoming_stock_shipments`

OR product_name ILIKE ANY(...) OR product_description ILIKE ANY(...)`. |

## Step-by-step

1. In `app/api/v1/incoming_stock/by_product.py`, add a helper `_resolve_product_candidates(db, query: str) -> tuple[list[str], list[str]]` returning `(codes, raw_patterns)`. Codes come from embedding; raw_patterns from `[f"%{query}%"]`.
2. Build the SQLAlchemy filter:
   ```python
   filter = or_(
       Product.product_code.ilike(any_(codes)),     # exact-code from RAG
       Product.product_code.ilike(any_(raw_patterns)),
       Product.product_name.ilike(any_(raw_patterns)),
       Product.product_description.ilike(any_(raw_patterns)),
   )
   ```
3. Surface `matched_candidates` in response so MCP layer can passthrough.
4. Update tool description in `catalog.py`.

## Acceptance

- `query=WC101` returns BOTH `SRTWC101` and `SRTWC101-RL` rows.
- Response includes `matched_candidates: ["SRTWC101","SRTWC101-RL"]`.
- `query=foobar123` (no hits) returns empty `data` with `matched_candidates: []` and helpful error message.
