## 3. Session and auth (S1)

Owner report: an expired session on the packing-list pages hung on a spinner until a manual
re-sign-in. Static trace (appendix H, 12 findings: 3 H, 6 M, 3 L); not reproduced in a browser.

**Most likely root cause.** The owner's state is "NextAuth cookie valid, FastAPI session
expired", which is the normal expired state because NextAuth never re-validates the FastAPI token
(`lib/auth-options.ts:184-242`). The packing-list detail fires about 10 parallel `apiFetch`
calls; all get a 401 `session_expired` (`dependencies.py:155-159`). `_maybeForceSignOut` checks
`_signingOut` (`lib/api.ts:199`), then awaits the body (`:201`), and only then sets the latch
(`:204`), so every call gets through and each runs an untimed `await signOut()` (`:211`, three
NextAuth round trips) before its `location.href` (`:215`). The first to finish flips NextAuth to
`unauthenticated`; the protected layout swaps in `ScreenLoader` and issues one soft
`router.push` with no timeout (`app/(protected)/layout.tsx:46-53`); later finishers re-assign
`location.href` and restart the navigation. React Query's `retry: 1` doubles the burst. Nothing
has a timeout, so the spinner can outlive the user's patience; a sign-in in another tab
broadcasts a session change, which is what "fixed" it.

**Second path, same symptom.** If `/api/auth/token` fails, `apiFetch` sends the request with no
Bearer (`lib/api.ts:138-139,482-497`); the backend's "Authentication required" 401 has no code
(`dependencies.py:289-296`), so no exit fires and every query just fails. If the token fetch
stalls, every query waits on the one shared `_tokenInFlight` promise with no timeout
(`lib/api.ts:134-157`): skeleton forever.

**Stale view-as** never redirects: the backend silently serves the admin's own data for a stale
header (`dependencies.py:192-213`) while the banner says "viewing as X", the store survives
logout (`lib/impersonation-store.ts:47`), and `/current` keeps a deactivated target's banner up
(`impersonation.py:194-212`).

**Answers.** One place converting 401 to a redirect? No: two (`lib/api.ts:195-219` for coded
401s, the protected layout for NextAuth `unauthenticated`), neither guarded against parallel
firing nor timed. Are 401s retried? Yes, once (`query-provider.tsx:38-39`,
`usePackingLists.ts:105,117`). Can navigation loop? No infinite loop; one bounded double bounce
after a soft-path re-sign-in, because the old token cache survives (appendix H row 6).

Fix: S1 of the standard (one synchronous latch, immediate `location.replace`, fire-and-forget
`signOut` with timeout, `session_missing` code, token-fetch timeout, no 401 retry, clear token /
query / view-as state on every exit, coded `impersonation_ended`).

## 7. Guards (cheap, automated, stop regressions)

All four are ratchets: today's violators go in a committed allowlist, a new violator fails, and a
fixed one must be removed from the allowlist (a stale entry also fails). They run in the existing
vitest / pytest jobs and in the pre-push hook's touched-vitest step.

### G1. Route-permission manifest (pytest, backend)

`tests/test_route_permission_manifest.py`: walk `app.main.app.routes`, recurse each
`APIRoute.dependant.dependencies`, and read the slug(s) out of every `require_permission*` /
`require_any_permission*` closure (`call.__code__.co_freevars` holds `permission_slug` /
`permission_slugs`) plus the router's module guard key. Emit
`{method, path, permissions[], any_of, module}` sorted, and:

1. assert it equals the committed `documentation/reference/route-permissions.json` (drift fails;
   `python -m scripts.dump_route_permissions` regenerates it);
2. assert every slug is in `PERMISSION_REGISTRY` (allowlist: the 5 above today);
3. list routes with no permission dependency, ratcheted (this is the section 6 backlog, made
   visible and unable to grow).

Introspection is needed because 319 `require_permission(...)` calls pass a constant, not a literal,
so a grep cannot see them.

### G2. Service-to-manifest test (vitest, frontend)

`lib/route-permissions.test.ts`: load `route-permissions.json`; for every service file under
`app/(protected)/**/services/`, `lib/*Service.ts`, extract `/api/v1/...` and the `/api/<alias>/...`
forms `apiFetch` rewrites (`lib/api.ts:334-355`), match each to a manifest path template, and
assert the file exports a `*_PERMS` object containing every slug those routes require (S4.1).
A second assertion: any component file importing a service from another module directory must
reference that service's `*_PERMS` (S4.5, the PR #1413 class). Ratchet allowlist for today.

### G3. Stuck-pattern ratchet (vitest, frontend, static)

`app/never-stuck.test.ts` fails a new file that contains any of:

- a `use*Query` destructure with `data` + `isLoading` / `isPending` and no `error` / `isError` /
  `status` (baseline 211);
- `isLoading || !` followed by a skeleton return;

#### Patterns observed

1. Cross-module reads without a gate (highest impact): the packing-list detail pages are `procurement.*` pages whose Proforma invoices, Shipment lines, Details and SPO tabs all read `/scm/*` endpoints that need `scm.dashboard.view`. The tab list is a static array (TAB_ORDER) and the shared `PackingListProvider` fetches source invoices unconditionally. PR #1413 is not on this branch.
2. Procurement BE routes mostly have no slug, so many FE "missing gate" cases have no 403 to hide; the exposure is the reverse (any authenticated user can call them). Worth a separate BE finding.
3. Permission-gated SCM writes are almost never gated in the FE: `scm.reorder.run` (SO, PO, SPO planner, photos), `scm.config.manage` (never referenced in FE at all), `scm.policy.manage` on market topics. Existing gates (plan, reset, PI upload/convert) show the intended pattern.
4. Components branch on `isLoading` and `?? []` only. Error handling is good in the reorder tree (ReorderPlanView, PlanLinesSection, PoWorklistView, CoverageTimelinePanel, PlanExceptionsView) and the dashboard grids, but weak in packing-list tabs, cost-price detail/lines/history, product-suppliers grid, and all SCM list grids.
5. Detail pages use `isError || !data` => "not found", which turns 403 and 5xx into a 404 look. A `Skeleton` guard on `isLoading || !data` (cost-price detail) is worse: it never resolves.
6. `scm/layout.tsx` gates the whole tree on dashboard.view, so SCM page-level D defects are largely closed, but the single slug over-gates reorder.run/policy.manage pages.
7. Where an error IS rendered (SpoPlannerTable, PackingListTimelineTab) it is the raw server string ("Permission required: scm.dashboard.view"), with no friendly access message.

#### Patterns observed

1. DataGrid has no error state, so every list built on it that does not add its own `isError` branch turns any 4xx/5xx into "No data available" (about 22 lists in scope). It is the largest single cause of the false-empty defect and a fix in `data-grid-table.tsx` (accept `isError`/`error` and render an inline notice) would cover most of the L/M list rows at once.
2. Detail pages use `isLoading || !entity` (infinite skeleton) or `!entity` (false "not found") with no `isError` branch: contacts/[id], teams/[id], automation/[id], email-templates/[id], email-theme, users/[id] layout, AccessAgentDetail.
3. Cross-slug secondary reads: pages gated by their own slug fetch pickers or catalogs that need a different slug (`roles/select`, `users/select`, `respond-workspaces/select`, `contact-access-types/`, `market-segments/`, `inventory/stock-visibility`, `email-templates`, `access-agents`). On 403 they degrade to an empty picker, and several are then saved back as empty values.
4. Swallow-by-design: `.catch(() => [])`, `if (!response.ok) return []`, `data = []` defaults, and the settings layout's default object. Each converts a 403 into plausible-looking data.
5. Sidebar is the only gate for nearly all of `user-management/*` and about 20 `system-management/*` pages (no `RequireAccess`). Integrations has no slug even in the sidebar (menu.config.tsx:880-883).
6. Action buttons (Add/Edit/Delete/Retry/Run/Sync/Export) are almost never gated by the matching `.add/.edit/.delete/.manage` slug; the user finds out through a 403 toast. Counted as one pattern, not rows. Exceptions that do it right: chatbot domains/kinds (`chatbot_config.manage`), app-store (`system.modules.manage`), ContactsList (`users.view/add`), users/actions.tsx, logs tabs.
7. `useRoleSelectQuery` stores the error body as data (toast then `response.json()`): a distinct crash-class bug, not just an empty state.
8. Backend gaps seen while tracing (out of FE scope): auth-only endpoints behind superadmin-only menu entries (jobs, import-logs, scheduled-tasks incl. PATCH/run-now, health summary, work-calendar PUT, mcp-tools, settings social/notifications/smtp, revision-configs PUT, contact market-segments/attachment-types PUT).

#### Patterns observed

1. **`dealer-kit` is one slug deep on the FE and five slugs deep on the BE.** The layout gates `dealer_kit.page.view` (`dealer-kit/layout.tsx:7`). The BE splits the section across `page.view/edit/publish`, `edition.approve`, `price_tag_requests.view/process`, `tag_templates.view/manage` and `library.manage`. The FE never checks any of the latter. Price-tag requests and tag templates are the first screens that split cleanly, and they are also the ones that false-empty.
2. **Price-tag request detail is a view page that fires a `process`-only call.** `line-pricing` (`price_tag_requests.py:267`) runs on mount for every viewer. The result is a wrong number (`RM 0`) rather than a visible error.
3. **Fetch effects with no `.catch`.** `PriceTagRequestsList`, `PriceTagRequestDetail`, `RequestTagDesignerShell` and `TagTemplatesList` all use `fetch().then().finally()` or `try/finally`. A rejected fetch leaves state at its initial value (`null` or `[]`), which the render treats as "no data" or "not found". `isError` does not exist in these because they bypass React Query.
4. **`isLoading`-only branching in master data.** Six list screens, five detail pages and four product-detail tabs destructure `isLoading` and never `isError`. The shared `DataGrid` defaults to "No data available" (`components/ui/data-grid-table.tsx:1085`) and has no error slot, so every false empty in this scope goes through that one fallback. `PanelDataGrid` has an `error` prop that the product tabs do not use.
5. **Shared select hooks turn a 403 into a cached empty success.** `master-data-management/shared/hooks/use-*-select-query.ts` toast once, then `return []`. With `staleTime: Infinity` and a 60-minute `gcTime`, the empty list sticks. They are imported from 15 files, so the defect reaches `project-sales`, `procurement-management`, `user-management` and `scm` too (outside this scope's files, inside its code).
6. **Cross-module reads without a gate.** Product Overview calls `projects.types.view`. Brand editors call `user_management.reference_data.view`. Sales agent tabs call `scm.dashboard.view` and `inventory.stock_transfers.view`. Flyer spec proposals call `dealer_kit.page.view`. In every case the FE checks only the host page's slug.
7. **Where it was done right** (copy these): `ProductSpecificationsTab` (read gating, write gating, raw error shown), `SalesAgentCustomersTab` (`isError` handled, `canEdit` gated), `FlyerSpecReviewScreen` (skips the call without the edit slug, explains why), `FlyerReadingsList`/`FlyerReviewScreen`/`SpecProposalSection` (explicit error alerts), `ProductSuppliersTab` and the Suppliers tab gate (`procurement.product_suppliers.view` matches the BE), `ProductsList` (error card), `StockTransfersPanel` (error card).
8. **Many master-data routes carry no per-slug permission at all.** `master_data/products.py` (every route), `products_select.py`, `ai_extract_field.py`, `field_linkage.py`, `respond_contacts_select.py`, `product_attachments.py` (list, get, create, update, delete), `marketing/promotions*.py`, `marketing/promotion_products.py`, `inventory/stock.py` (balance, dashboard, alerts, ledger), and `audit/audit_logs.py` (partly) use `get_current_user[_or_api_key]` only. The FE "gate matches" there is vacuous. These are backend gaps for the other audit lanes, not FE defects, and they explain why several product-detail tabs show no 403 today. `ai_extract_field.py:60` (an LLM call) has no permission check at all.
9. **403 text is mostly lost.** Services in `brands`, `product-categories` and `inventory-management/stock` throw fixed strings ("Failed to fetch brands", "Failed to fetch stock balance") instead of calling `extractApiError`. The global toast in `providers/query-provider.tsx` therefore cannot tell a permission failure from an outage.

#### Patterns observed

1. **Hand-rolled `useEffect` plus `try/catch(toast)` lists with no error state** (tickets list, kanban, detail; `WorkflowSubmissionEditor` `new`). These are the worst cases: the loading flag flips to false and the empty or skeleton branch wins. The tickets module has no react-query and no `isError` anywhere.
2. **`isLoading || !data` collapsed into one skeleton** (ticket detail, workflow submission detail, workflow builder). A 403 or 404 becomes an infinite skeleton. The `!data` branch needs `isError` handling.
3. **`!data` rendered as "not found"** (complaint, forms, attachment, SLA tracker details). This hides 403, 500 and module-disabled errors behind a not-found message.
4. **Helper pickers default `data = []` and never read `isError`** (users select, contact-access-types, root-cause and resolution selects, role select, project search, `SearchableSelect` catch to `[]`). They look correct but are empty for roles lacking a slug unrelated to the screen. Slugs involved: `user_management.users.view`, `user_management.reference_data.view`, `user_management.roles.view`, `master_data.complaint_*.view`, `projects.projects.view`, `sla_management.message_snippets.view`.
5. **Sidebar-only gating**: the folders contain one `RequireAccess` (conversations). Every other gated menu item (`complaint_root_causes`, `complaint_resolutions`, snippets, KPI except in-page, workflow definitions) is open to deep links. Conversely, several sidebar entries carry no slug where the backend does (form SLA config view/manage).
6. **Action buttons never check the slug the backend requires**, even where adjacent code does (ticket mutations, SLA escalate on three surfaces, complaint PDF, resource upload, bulk import, bulk archive and delete). Modules that do check (workflow forms, complaint approve and close, SLA widget) show the intended pattern.
7. **Cross-module reads sit under another module's guard.** The complaint, ticket and PR detail pages read `sla`, `forms` and `resources` module routes. For non-admin users in a tenant where one module is disabled, the error is "Module not enabled: x", which the UI renders as an empty tab or section.
8. **Backend gaps seen in passing** (not FE defects): complaints delete, bulk-delete, update, attachment link and unlink have no permission (`complaints/complaints.py:347,1249,1649`); forms CRUD has none; resource single-record delete and archive have none; `/integrations/logs` (Smart Linkage list, reachable by deep link only) has none; `/complaints/{id}/fulfilment-orders` reads orders with none.

#### Explicit answers

**(a) Most likely root cause of the packing-list hang.** The owner's state is "NextAuth cookie valid, FastAPI session expired". The code path:
1. The `[id]/layout.tsx` provider plus the shell fire about 10 parallel `apiFetch` calls. All get a 401 `{detail:{code:'session_expired'}}` (`dependencies.py:155-159`).
2. Each one calls `_maybeForceSignOut` (`api.ts:549`). The `_signingOut` guard is racy (check at :199, await at :201, set at :204), so every call proceeds into `await signOut({redirect:false})` (:211). That is 3 untimed NextAuth requests each, on a single slow Node process.
3. The first signOut to complete broadcasts and re-reads the session, so `useSession` becomes `unauthenticated`. `app/(protected)/layout.tsx:52-53` replaces the page with `ScreenLoader` and fires a soft `router.push` (:48). The hard `location.href` (:215) of each caller only runs after its own signOut resolves, and later ones restart the pending navigation.
4. With retries (#9) doubling the burst and no timeouts anywhere (#4, #5), the spinner can sit for a very long time. If the soft push does not land and a signOut fetch stalls, it never ends, until a sign-in in another tab broadcasts a new session and re-renders the tab.

Secondary candidate with the same symptom family: #3 + #4. When `/api/auth/token` fails or stalls, the requests go out with no Bearer (an uncoded 401, so no redirect), or they hang on the shared in-flight token promise (skeleton forever).

**(b) Is there a single place that converts 401 into signOut/redirect with callbackUrl, and is it guarded against firing N times?** Not single. There are two:
- `lib/api.ts:195-219`: code-gated 401 -> `signOut({redirect:false})` -> `location.href = /signin?callbackUrl=path+search+hash`.
- `app/(protected)/layout.tsx:35-50`: NextAuth `unauthenticated` -> `router.push('/signin?callbackUrl=...')`.

Both run on every forced sign-out: the first triggers the second through the session broadcast. That gives 1 soft plus N hard navigations. The api.ts guard is NOT effective against parallel 401s, because the flag is set after an `await`. The layout path has no guard, but it runs once per status change. Neither has a timeout or fallback. Uncoded 401s (no token, auth exceptions) reach neither path.

**(c) Do 401s get retried by react-query?** Yes. The global default is `retry: 1` (`providers/query-provider.tsx:38-39`), and the packing-list hooks set `retry: 1` explicitly (`hooks/usePackingLists.ts:105,117`). No retry predicate excludes 401/403, and the service errors do not carry the status.

**(d) Can router.push/replace or signIn redirects loop?** No infinite loop found. `/signin` (`app/(auth)/signin/page.tsx`) never auto-redirects a signed-in user. It only `router.push`es after a successful `signIn` (:98-104), so there is no signin-to-protected ping-pong. The bounded double-bounce is #6: after a soft-path re-sign-in, a stale `_cachedToken` (soft 300s window, never cleared on that path) can 401 `session_expired`. That forces one more sign-out, which is a hard nav, so state resets and the second sign-in sticks. The other "multiple redirects" are the soft-plus-N-hard navigations of #1 / #2. Impersonation cannot loop, because the BE silently ignores a stale header (#7).

#### Patterns
1. **No fetch timeout anywhere.** `apiFetch` (lib/api.ts:540) and the token fetch (lib/api.ts:138) call bare `fetch`. 2. **Retry is only React Query's `retry:1` (provider default).** No jitter or classification: mutations and non-idempotent POSTs are not retried (good), but GETs retry without a timeout so the worst case doubles the hang.
3. **Poll-on-status-without-ceiling.** Every job poll stops only on a terminal value written by the worker. Anything that strands the row (worker down, SIGKILL in a deploy, Redis eviction) leaves the UI polling forever (some even in background tabs: low-stock, autocount pull, both `refetchIntervalInBackground: true`).
4. **BE sweepers exist for 4 families only:** import_jobs (`_reconcile_orphan_import_jobs`, scheduler heartbeat), downloads/exports (`download_service.fail_stale`, 20 min, swept on read), PO/schedule extraction (`project_extraction_recovery_service`), chatbot delegated turns (`chatbot_turn_sweep`, 10 min), autocount pull build (`advance_building_pulls`, 60 min BUILD_EXPIRY). No sweeper found for flyer readings, flyer spec batches, reorder runs, spec preview, media.
5. **Failure-in-except blind spot**: task `except` blocks (flyer_read_tasks.py:171-181, export_tasks.py) never run when the work-horse is SIGKILLed (deploy recreates worker, 10 s grace). Only families in (4) cover that.
6. **Queued with worker down**: `_reconcile_orphan_import_jobs` deliberately skips a row whose RQ job still exists in `queued` (task_scheduler.py ~l.140-150), so "worker not draining" yields `queued` forever; no "still queued after N min" state in the UI either (only downloads time out via the 20 min fail_stale).
