# TCK-2026-000028 - Form SLA: fix auto-scan tier progression + user-facing manual escalate

> **Source:** directors' session 2026-06-17 (priority #1). Grilled 2026-06-17.
> **Priority:** high · **Category:** feature + bugfix
> **Dependencies:** none. TCK-2026-000029 later wires WhatsApp onto the escalation event this ticket emits.

## Premise correction (verified in code)

Form SLA escalation is **already system-driven, NOT n8n**:

- Scheduled task `form_sla_overdue_scan` (migration `179_seed_form_sla_overdue_scan`) - **every 2 minutes**, `enabled=true`, UTC.
- Heartbeat `task_scheduler.py:_scheduled_tasks_heartbeat` (every 10s) dispatches due tasks → `_handler_form_sla_overdue_scan` (`task_scheduler.py:164`) → `FormSLAOrchestrator.scan_overdue_and_escalate()` (`form_sla_service.py:236`).
- Runs on the **worker container only** (`ENABLE_SCHEDULER=true`; API/blue-green containers gated off to avoid double-fire - `main.py:182`).
- Covers complaint / stock_inquiry / purchase_request / sponsorship_form.
- n8n drives **only conversation SLA** (`/api/v1/sla/integration/escalate`), never form SLA.

So no scheduler needs building. This ticket does two things: **(A)** fix a latent bug that freezes the auto-scan after the first hop, and **(B)** add a manual, user-triggered force-escalate.

## Goal

### A. Fix auto-scan tier progression (bug)

Current idempotency guard (`form_sla_service.py:261-267`):

```python
if (tracker.escalated_at is not None
    and tracker.current_tier_started_at is not None
    and tracker.escalated_at >= tracker.current_tier_started_at):
    continue  # skip
```

When escalating into tier 2, the code sets `escalated_at = now` **and** `current_tier_started_at = now` (`:311-312`), so at tier 2 the guard is permanently TRUE → **auto-scan can never escalate tier 2 → tier 3.** Only the first hop ever fires.

**Fix:** delete the `escalated_at` guard entirely. Gate escalation solely on the overdue check (`now > due_at` or `now > due_at_resolution`). `due_at` is already derived from `current_tier_started_at + working(response_hours)`, so the gate is effectively "has the current tier's clock elapsed." Each escalation resets `current_tier_started_at = now` and pushes `due_at`/`due_at_resolution` forward, so the next tier won't fire until **its** clock elapses - self-idempotent, no separate guard needed. At the top tier `next_tier` lookup returns None → escalation naturally stops (row stays open/overdue). `escalated_at` is kept for display/event context, just no longer gates.

### B. Manual force-escalate (feature)

Authorised user force-escalates an in-progress form SLA row **to the next tier, before breach**, from the entity detail page. Auto-scan remains the unattended-breach safety net. Manual bypasses only the overdue gate; everything else (tier+1, reassign, clock reset, due recompute, event log, notify) is identical to auto.

Covers: complaint, stock_inquiry, purchase_request, sponsorship_form.

## Design decisions (from grilling)

- **Manual target tier:** next tier only (`current_tier + 1`). No tier picker, no jump-to-management. To climb further, click again.
- **Shared path:** extract the inner escalation block (`form_sla_service.py:269-338`) into `_escalate_tracker(tracker, *, reason, trigger, triggered_by_id=None)`. Both the scan loop and the manual endpoint call it, so behaviour can't drift. The only difference is the caller: scan passes `trigger="auto"` and pre-filters on overdue; manual passes `trigger="manual"`, `triggered_by_id=actor`, and skips the overdue gate.
- **Manual vs auto in reporting:** add two columns to `conversation_sla_event_logs`:
 - `trigger` (text, `'auto'|'manual'`, default `'auto'`)
 - `triggered_by_id` (nullable FK → users.id; the human who clicked; NULL for auto)
 - (`assigned_to_id` stays the escalation **target**, not the actor.) Consumed by the KPI dashboard (TCK-2026-000032).
- **RBAC:** new permission slug `sla.form.escalate`, granted to **all roles** (every authenticated user who can reach the entity can escalate). Slug exists so it can be tightened later, but default grant is broad. Holder can escalate **any** row (no ownership check).
- **WhatsApp on escalation (cross-ref TCK-2026-000029):** the escalation **recipient** (the resolved new assignee at the target tier) receives a WhatsApp **only if that user has `notify_whatsapp` on + a linked RespondContact** (per TCK-2026-000031). 24h-window aware: contact's conversation window open → normal text; window closed → approved template. There is **no per-escalate WhatsApp checkbox** - the recipient's own channel pref governs, identical to auto-escalate. Directors are typically tier-3 users, so set `notify_whatsapp` on for them.
- **No resolvable next-tier assignee** (no `agent_id`, no team for the target tier, or empty round-robin): manual **hard-fails 422, tracker untouched**, with a specific message (`"No tier-N team configured for this policy"` / `"No agents available for tier N"`). Auto-scan keeps its existing silent-skip - manual is interactive so silence is wrong.
- **Top tier** (no next tier) → 422 `"Already at highest tier"`. **Resolved row** → 422 `"SLA already resolved"`.
- **Reason:** required free-text on manual; stored on the event log `reason` and on `tracker.escalation_reason`.

## Files to change

### Backend

- `app/services/form_sla_service.py`:
 - Extract `_escalate_tracker(tracker, *, reason, trigger, triggered_by_id=None)` from the inline block; it advances tier, resolves next-tier assignee, recomputes due (working hours), writes the `escalation` event log (now with `trigger` + `triggered_by_id`), notifies new assignee (`_notify_assignee(kind="escalated")`). Returns the resolved assignee or raises a typed `AppException` when no assignee resolves (so manual can 422; scan catches and skip-counts).
 - `scan_overdue_and_escalate()`: remove the `escalated_at` guard; keep the overdue filter; call `_escalate_tracker(..., trigger="auto")`; on the no-assignee exception, increment `skipped_count` (preserve current silent-skip behaviour for auto).
 - New `escalate_form_tracking(tracking_id, *, reason, actor_user_id)`: load row, assert `source_entity_type ∈ FORM_SLA_TYPES`, not resolved, not top tier; call `_escalate_tracker(..., trigger="manual", triggered_by_id=actor_user_id)`; best-effort side effects (catch+warn, never raise post-commit - CLAUDE.md rule).
- `app/api/v1/sla/form_sla_tracking.py` (new router, mounted under the `sla` domain in `app/api/v1/__init__.py`, behind the existing module guard):
 - `GET /api/v1/sla/form-tracking?source_entity_type=&source_entity_id=` → active stage row(s): tier, due_at, assignee (resolved to name - **no UUIDs**), trigger history.
 - `POST /api/v1/sla/form-tracking/{tracking_id}/escalate` body `{reason: str}` → `escalate_form_tracking`. Require `sla.form.escalate`.
- RBAC seed: add `sla.form.escalate`, grant to **all roles** (broad default).
- Alembic migration `18x_form_sla_event_trigger`:
 - Add `trigger` + `triggered_by_id` to `conversation_sla_event_logs`.
 - **Rollout reset (avoid escalation burst):** for unresolved trackers with `current_tier >= 2` and `source_entity_type ∈ FORM_SLA_TYPES`, set `current_tier_started_at = now` and recompute `due_at`/`due_at_resolution` from the current tier's hours, so each restarts its SLA window at deploy time. Without this, dropping the guard would escalate every already-overdue frozen tier-2 row on the first 2-min tick. (Conversation-SLA rows untouched.)

### Frontend

- `components/common/FormSlaEscalateButton.tsx` (new, shared): shows current tier + due (KL wall-clock); "Escalate" opens a modal with a **required** reason textarea (no tier select). Submit → service → invalidate + toast. Plain modal, not a destructive `AlertDialog`.
- `services/formSlaService.ts` (new): `getFormTracking`, `escalateFormTracking` (hook → service → `lib/api-client`, `extractApiError`).
- Mount the button + an always-rendered SLA section on the four detail pages (complaint, stock inquiry, purchase request, sponsorship form). Empty-state when no active tracking: "No active SLA stage".

## Acceptance

- **Auto-scan fix:** a tier-2 row past its due escalates to tier 3 on the next scan tick (previously frozen). A freshly-escalated row does **not** re-escalate on the next tick (clock reset + future due). Top-tier overdue row stays put (no next tier). After deploy migration, no burst - existing tier-2 rows restart their clocks.
- **Manual:** clicking Escalate on a tier-1 complaint (not yet overdue) moves it to tier 2, reassigns per policy, writes one `escalation` event log with `trigger='manual'`, `triggered_by_id=<actor>`, `reason=<user text>`, new assignee notified. Verified on all four form types.
- Manual on top tier → 422; resolved → 422; next tier has no team/assignee → 422, **tracker unchanged**.
- Any authenticated user with the (broadly-granted) slug can escalate; user lacking it → 403.
- Escalation recipient with `notify_whatsapp` on + linked contact → WhatsApp fires (text if window open, template if closed); recipient with it off → no WhatsApp, in-app + email still fire.
- Event log distinguishes manual from auto via `trigger`.
