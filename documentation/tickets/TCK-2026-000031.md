# TCK-2026-000031 - User ↔ RespondContact link + admin-editable phone + per-channel notification prefs

> **Source:** directors' session 2026-06-17. "Toggled per user, key in each user's phone, link to respond contacts." Grilled 2026-06-17.
> **Priority:** high · **Category:** feature · **Foundation for** TCK-2026-000029, TCK-2026-000030.
> **Dependencies:** none. **Land this first.**

## Goal

1. Make `users.contact_number` editable in the **admin** user-management form.
2. Link a CRM user to a RespondContact so we can resolve their `respond_io_id` for WhatsApp.
3. Add **per-channel notification toggles** per user.

## Design decisions (from grilling)

- **Link model:** one-to-one nullable FK `users.respond_contact_id` → `respond_contacts.id`. Supports **both** manual and auto linking:
 - **Manual:** admin sets it via a RespondContact picker.
 - **Auto:** if unset, resolve by **E.164-normalized** phone match (`users.contact_number` ↔ `RespondContact.phone_number`), only on a **single exact** match, then cache the id on the user row.
 - Resolution order in `resolve_user_respond_io_id(user)`: explicit `respond_contact_id` → else normalized phone match → else None.
- **Phone safety:** normalize both sides to **E.164** (Malaysia `60…`) before matching; add a **unique constraint** on `users.contact_number` (nullable) so two users can't claim the same number. `RespondContact.phone_number` is already unique → deterministic 1:1.
- **Per-channel prefs** (new columns on `users`, default to safe/off until a contact is linked):
 - `notify_whatsapp` (bool) - escalation + new-assignment WhatsApp pings (TCK-29).
 - `notify_whatsapp_summary` (bool) - daily summary WhatsApp template (TCK-30).
 - keep existing `daily_sla_summary_subscribed` (bool) - **email** summary.
 - in-app is always on.

## Background (verified)

- `users.contact_number` exists (`app/models/user.py:27`, migration 118), in `UserCreate`/`UserUpdate` schemas + responses - but not wired into the admin profile edit form in practice.
- `users.daily_sla_summary_subscribed` (bool, migration 125) gates the email summary; self-service toggle `account/components/daily-sla-summary-preference.tsx` + PATCH under `/api/v1/notifications/preferences/daily-sla-summary`.
- `RespondContact` (`app/models/access.py:120`): `phone_number` unique, `respond_io_id`. **No user link today.**

## Files to change

### Backend

- Migration: add nullable FK `users.respond_contact_id` → `respond_contacts.id`; add `notify_whatsapp`, `notify_whatsapp_summary` (bool, default false); add a **unique constraint on `users.contact_number`** (after normalizing existing data - normalize in the same migration, fail loudly on a collision so it's resolved by hand).
- `app/models/user.py`: new columns + the relationship.
- Service helper `resolve_user_respond_io_id(user)` (resolution order above); on first successful phone match, persist `respond_contact_id` (idempotent JOIN-based cache).
- Phone normalization util (E.164, default region MY) reused by the form, the matcher, and the migration.
- `scripts/backfill_user_respond_contact.py`: set `respond_contact_id` where a single normalized phone match exists; re-runnable; corrects prior mismatches.
- Endpoints:
 - Admin `PUT /api/v1/user_management/{user_id}`: accept `contact_number`, `respond_contact_id`, `notify_whatsapp`, `notify_whatsapp_summary`.
 - Self: extend the notification-preferences endpoints to read/write the channel matrix.

### Frontend

- `user-management/users/[id]/components/user-profile.tsx` (+ `forms/user-profile-schema.ts`): phone input (E.164-aware validation), a **searchable RespondContact picker** showing **name + phone, never the UUID** (cursor rule), and the three toggles.
- `user-add-dialog.tsx`: confirm `contact_number` is captured at create.
- Account settings: surface the same channel matrix for self-service (shared component with the existing daily-summary toggle).

## Acceptance

- Admin sets phone + picks a contact + flips WhatsApp on → persists; `resolve_user_respond_io_id` returns the contact's `respond_io_id`.
- Leave `respond_contact_id` blank but set a phone that uniquely matches a RespondContact → auto-link resolves + caches on first use.
- Two users cannot be saved with the same normalized phone → constraint blocks it.
- Backfill links unique matches; second run is a no-op.
- Picker shows name + phone, no UUIDs.
- Channel matrix round-trips for admin (any user) and self-service (own user). No linked contact + WhatsApp on → downstream sends (TCK-29/30) skip gracefully.
