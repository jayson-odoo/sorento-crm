# TCK-2026-000030 — Conversation SLA daily summary via WhatsApp (bounded template)

> **Source:** directors' session 2026-06-17. "Send conversation SLA summary as email / WhatsApp, toggled per user." Grilled 2026-06-17.
> **Priority:** high · **Category:** feature
> **Dependencies:** TCK-2026-000031 (per-user phone + link + `notify_whatsapp_summary` toggle).

## Goal

The daily conversation-SLA summary already sends **in-app + email**. Add a **WhatsApp** delivery, gated by a dedicated per-user toggle. Because the send is almost always out-of-window, WhatsApp delivery is a **bounded template** (a few counts + a deep link), not the full text.

## Design decisions (from grilling)

- **WhatsApp form:** a **fixed-shape approved template** carrying bounded params — e.g. `outstanding`, `escalated_last_24h`, `resolved_last_24h` — plus a **deep link** into the CRM where the full summary lives. Full detail stays on email + in-app. (A template can't hold a long free-form digest; staff WhatsApp windows are closed at summary time, so text-in-window is not viable for a daily job.)
- **No management roll-up:** every user — directors included — gets only their **self-scoped** summary (their own assigned/outstanding rows). Team-wide aggregation is the KPI dashboard's job (TCK-2026-000032), not the digest.
- **Toggle:** a **separate** `notify_whatsapp_summary` pref (TCK-31), distinct from escalation's `notify_whatsapp`. A user can want real-time escalation pings on WhatsApp but not a daily digest, or vice versa. Email summary stays governed by the existing `daily_sla_summary_subscribed`; in-app always.

## Background (verified)

- `app/services/user_sla_daily_summary_service.py` — `run_user_sla_daily_summary()` (`:189`), bodies via `_build_bodies()` (`:99`), HTML email + unsubscribe token. Scheduled (per-user, daily) through the task scheduler.
- WhatsApp send: `respond_messaging_service.send_text_or_template()` on the `respond_io` queue (template path when window closed).

## Files to change

### Backend

- `app/services/user_sla_daily_summary_service.py`:
  - Compute the three bounded counts per user (already implicit in the summary data).
  - For each user with `notify_whatsapp_summary=True` + resolvable RespondContact (`resolve_user_respond_io_id`, TCK-31): enqueue a `respond_io` send of the `sla_daily_summary` template with the counts + deep link. The deep link targets a CRM "my SLA summary" view (reuse `/my-pending` data, `sla_tracking.py:267`, or a dedicated summary page).
  - Self-scoped only — no aggregate-across-assignees branch.
- Register `sla_daily_summary` in `respond_template_defaults` with its param mapping (3 counts + URL).
- The email/in-app summary path is otherwise unchanged. Quick confirm SMTP resolves (DB SystemSetting → env, `notification_email.py:14-36`).

### Frontend

- Account settings: extend the channel toggles (shared component with TCK-31) to include `notify_whatsapp_summary`. Reads/writes the pref.

## Acceptance

- A user with `notify_whatsapp_summary` on + linked contact receives one WhatsApp template per scheduled run, with correct counts + a working deep link; email + in-app summary unchanged.
- Toggle off OR no linked contact → no WhatsApp summary; other channels still fire.
- Directors receive the same self-scoped summary as everyone else (no special roll-up).
- `notify_whatsapp_summary` and escalation `notify_whatsapp` are independent (one on, one off behaves correctly).
