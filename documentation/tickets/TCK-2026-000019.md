# TCK-2026-000019 - Packing list + promotion create email: warn on unknown products

> **Source ticket:** `TCK-2026-000019` (status: draft)
> **Priority:** high · **Category:** feature
> **Dependencies:** none. Self-contained.

## Goal

When a packing list (or promotion) is created via the external webhook, surface every `product_code` in the payload that does NOT exist in master data as a **warning** in:

- the in-app notification body,
- the success email (HTML + plain),
- the create response payload (so n8n / portal can echo back).

Do NOT block creation - warnings only.

## Files to change

| File | Change |
|------|--------|
| `sorento_crm_backend/app/services/procurement_service.py:504` (`InboundShipmentService.create_shipment`) | Track `unknown_product_codes: set[str]` during line processing (product lookup misses). Return as part of the create result. |
| `sorento_crm_backend/app/services/marketing_service.py:496` (`PromotionService.create_promotion`) | Same pattern - collect missing `product_code`s from promotion-product lines. |
| `sorento_crm_backend/app/api/v1/external/packing_lists.py` (lines 26 - 143) | Pass `unknown_product_codes` to notification helper + echo in response. |
| `sorento_crm_backend/app/services/attachment_notification_helper.py:262 - 333` (`notify_after_external_attachment_entity`) | Add kwarg `warnings: list[str] = []`. If non-empty, render an HTML `<section class="warnings">` block + plain-text equivalent: *"Products not found in system (these lines were skipped or imported without master-data linkage): code1, code2, …"*. |
| Same file, `notify_after_external_promotion_created` (lines 549 - 585) | Mirror the same `warnings` kwarg + render. |
| Schema files for the create responses | Add `unknown_product_codes: list[str]` to the response model. |

## Step-by-step

1. Audit the existing product-lookup branch in `create_shipment` - confirm whether unknown codes are silently skipped today or raise. Behaviour stays the same; only the visibility changes.
2. Surface `unknown_product_codes` via the return.
3. Plumb through the route handler into the notification helper.
4. In the notification helper, render the warnings block ONLY when non-empty. Keep the existing email body intact for the success path; warnings appear as a clearly-styled section near the top so the user sees them.
5. Repeat for the promotion path.

## Acceptance

- Create packing list with 13 lines, 2 using fake codes → response carries `unknown_product_codes: ["FAKE1","FAKE2"]`; success email contains the warning block listing those two; in-app notification body includes the same list.
- Create promotion with 5 product lines, 1 unknown → same behaviour.
- Empty warnings → email renders exactly as before (no empty block).
