3What each step ships

Five steps, shipped one at a time. The two in the dashed box can run side by side.

S0→ S1S3→ S2→ S4
S0Groundwork and a clearer history No hand test needed

Behind the scenes: a user may now be phone-only, emails match regardless of capitals, each WhatsApp contact belongs to at most one user, and every entry in the history says who did it and how. Existing staff whose phone exactly matches one WhatsApp contact are linked to it; you get that list by name to check before it goes live.

TodayA nightly job or an n8n update shows as "System" in a record's history, and an admin using "view as contact" is recorded as the contact.
AfterThe history reads "Background job for Aisyah", "Integration: n8n as Ops Bot", "Nurain on behalf of Aisyah", "Aisyah (phone)".

Your part: read the list of automatic phone-match links before it merges. Nobody signs in any differently.

S1Sign in with a phone number Needs your hand test

The sign-in page gets one field, "Email or phone number". Type an email and you get the password step as today. Type a phone number and a 6-digit code arrives on WhatsApp.

TodayOnly email and password. Typing an unknown email says "User not found. Please register first.", which tells a stranger who has an account.
AfterA staff member types 012-345 6789, gets a code on WhatsApp, enters it, and is in. An unknown email and a wrong password get the same answer.

Your hand test: sign in on your phone with your own number, and once with email and password.

S3You create and link users Needs your hand test

A new "Salesperson accounts" list under User Management shows every salesperson contact and whether they have a user yet. "Create user" opens the usual Add user form already filled in from the contact. A contact's page gets a "User account" part with Create user and Link existing user.

TodayThere is no way to give Aisyah, a retail salesperson with only WhatsApp, a user; every user needs an email, and nothing shows which salespeople still need setting up.
AfterYou open Salesperson accounts, click Create user on Aisyah's row, check her name, phone, Salesperson role and companies, save. Her row turns "Linked".

Your hand test: create one salesperson from the list, and link an existing staff member who is also a salesperson (the form offers "Link to <name> instead" when the phone is already a user's).

S2The portal uses the same sign-in Needs your hand test

For a person you have set up, the portal link they already have now signs them in as their user. Same card, same code, same forms, same submissions. For a contact you have not set up, nothing changes at all.

TodayAisyah taps her months-old WhatsApp link, enters the code, and uses the portal on a separate portal-only session with no user behind it.
AfterShe taps the same link, enters the same code, lands on the same portal home, now signed in as her user. If you later give her a CRM role, "Open CRM" takes her there without a second sign-in.

Your hand test: open an old link for a set-up salesperson and for a dealer you have not set up; both should look exactly as before.

S4Screens to look after sign-ins Needs your hand test

The Users list gets a Kind filter (Staff, Salesperson, Portal) and a Sign-in column (Email, Phone, both). Each user's page gets a Sign-in part: email, phone and whether it is verified, linked WhatsApp contact, last sign-in and how.

TodayIf a salesperson's WhatsApp number changes, nothing tells you, and there is no one place to see how a person signs in.
AfterThe user shows "Needs attention: phone differs from WhatsApp contact" with "Use new number". Taking it signs them out everywhere; their next code confirms the new number.

Your hand test: filter the Users list by Salesperson, open one, and check the Sign-in part on your phone and on a laptop.

4Open questions

Not ruled yet. The plan is written to the recommendation; a different answer changes only what is listed under it.

1. Sign-in screen: one field or two tabs? (was Q7)

Recommend: one field, "Email or phone number". The page works out which you typed.
If two tabs instead: the page shows "Email" and "Phone" tabs and the person picks first. Only the sign-in screen changes; everything behind it stays the same.

2. Old portal sessions of people you set up (Q11)

Recommend: contacts you have not set up keep their portal session as today, with no end date. Once you set someone up, their old portal session stops renewing and ends within 30 days. Old WhatsApp links keep working for everyone.
If old sessions keep renewing for set-up people too: that person carries two separate sessions for good, and signing out of one does not end the other.

3. Admin "view as contact" (Q12)

Recommend: keep it, and record what the admin does there as "the admin on behalf of the contact".
If removed: admins can no longer see the portal the way a contact sees it, which is how portal problems are checked today.

4. Someone loses their phone (Q13)

Recommend: an admin changes the number on the user. That signs them out everywhere, and their next code confirms the new number.
If people change it themselves: they need a second way to prove who they are, which a phone-only person does not have, and a new self-service screen gets built.

5. A salesperson's phone already belongs to a staff user (Q14)

Recommend: the Create user form stops and offers "Link this contact to <name> instead". You decide; nothing links by itself.
If linked automatically: quicker, but a link is made without you seeing it, which goes against your rulings on Q3 and Q4.

6. How long a phone or portal sign-in lasts (Q15)

Recommend: 30 days, renewed while in use, the same as the portal today.
If shorter (for example 8 hours): salespeople ask for a WhatsApp code far more often, and each code is a WhatsApp message sent.

6Out of scope and risks

Not in this plan

  • Creating users automatically, in bulk or at sign-in (your Q3 and Q4 rulings). Comes back only if you ask.
  • Switching off the old portal session for contacts you have not set up.
  • SMS codes. Only if a salesperson cannot receive WhatsApp.
  • CRM permissions for salespeople (your Q8 ruling). Later a role change, no code.
  • Self sign-up by the public.
  • Rewriting the older "who did this" fields across every module; the history-trail work in #1281 decides that.
  • Stronger storage of sign-in sessions; logged as its own security job.

Risks

  • Only people you set up get the one sign-in. Until your list is done, the rest stay portal-only and their actions are recorded against their WhatsApp contact.
  • WhatsApp code message. If the approved code message is paused or rejected, phone sign-in stops; email and password still work. If its wording names the portal, you will be asked whether it can also be used for CRM sign-in before S1 starts.
  • No background worker, no codes, as already true for the portal.
  • Admins signing in by code is weaker than a password if a SIM is stolen; you accepted it, and it can be switched off for admins with one small change.
  • A changed WhatsApp number blocks that person's phone sign-in until you confirm the new number.
