3What each step ships

Four steps, shipped one at a time. The two in the dashed box can run side by side. S4 is dropped.

S0→S1S3→S2S4
S0Groundwork and a clearer historyNo hand test needed

Behind the scenes: a user may be phone-only, emails match regardless of capitals, each WhatsApp contact belongs to at most one user, and every history entry says who did it and how. Staff whose phone exactly matches one WhatsApp contact are linked to it; you get that list by name before it goes live.

TodayA nightly job or an n8n update shows as "System" in a record's history, and an admin using "view as contact" is recorded as the contact.
AfterThe history reads "Background job for Aisyah", "Integration: n8n as Ops Bot", "Nurain on behalf of Aisyah", "Aisyah (phone)".

Your part: read the list of automatic phone-match links before it merges.

S1Phone option on the existing sign-in pageNeeds your hand test

Your sign-in page gets an Email | Phone toggle. Email is today's page, untouched. Phone asks for the number, sends a WhatsApp code the same way the portal does, and signs in on the sixth digit.

TodayOnly email and password. Typing an unknown email says "User not found. Please register first.", which tells a stranger who has an account.
AfterNurain taps Phone, types 012-345 6789, gets a WhatsApp code, types it, and is in. An unknown email and a wrong password get the same answer.

Your hand test: on your phone, sign in once with Phone and once with Email; check the Email side looks exactly as today.

S3You create and link users, on your existing pages, with no email sentNeeds your hand test

Internal Users gets a User column and a "Create user" row action. Administrative Users' Add user form gets a WhatsApp contact field and loses the invitation tick box. Each contact gets a User account part; each user gets a Sign-in part with a "Send invitation email" button that asks before sending.

TodayCreating Aisyah needs an email, and with the tick box on by default she would get an invitation email the moment you save.
AfterOn Internal Users, Aisyah's row, Create user: the form is filled from her contact, Salesperson suggested. You click Add user. Her row shows her name; she gets nothing until she uses her portal link.

Your hand test: create one salesperson from Internal Users, link one staff member who is also a salesperson, and check no email arrived. Then send one invitation on purpose and see the confirmation.

S2The portal uses the same sign-inNeeds your hand test

For a person you have set up, the portal link they already have now signs them in as their user. Same card, same code, same forms. For a contact you have not set up, nothing changes.

TodayAisyah taps her WhatsApp link, enters the code, and uses the portal on a portal-only session with no user behind it.
AfterShe taps the same link, enters the same code, lands on the same portal home, now as her user. If you later give her a CRM role, "Open CRM" takes her there with no second sign-in.

Your hand test: open an old link for a set-up salesperson and for a dealer you have not set up; both look exactly as before.

S4Admin identity screens: dropped

Dropped by your 00:45 note. The Users list Kind filter and Sign-in column are gone; the one useful part, a user's Sign-in section, moved into S3 on the existing user page.

4Open questions

Not ruled yet. The plan is written to the recommendation; a different answer changes only what is listed under it.

1. When you change an existing user's email, keep the security notice? (Q18, new)

Recommend: keep it. It goes only to someone who already has an account, telling them their sign-in email changed. It never fires when you create or link a user, or when you add a first email to a phone-only user.
If no: that notice is removed as well, and no email about a user's account ever goes out unless you press Send invitation email.

2. Old portal sessions of people you set up (Q11)

Recommend: contacts you have not set up keep their portal session as today. Once you set someone up, their old portal session stops renewing and ends within 30 days. Old WhatsApp links keep working for everyone.
If old sessions keep renewing: that person carries two separate sessions for good, and signing out of one does not end the other.

3. Admin "view as contact" (Q12)

Recommend: keep it, and record what the admin does there as "the admin on behalf of the contact".
If removed: admins can no longer see the portal as a contact sees it, which is how portal problems are checked today.

4. Someone loses their phone (Q13)

Recommend: an admin changes the number on the user. That signs them out everywhere, and their next code confirms the new number.
If people change it themselves: they need a second way to prove who they are, which a phone-only person does not have, and a new screen gets built.

5. A salesperson's phone already belongs to a staff user (Q14)

Recommend: the Add user form stops and offers "Link this contact to <name> instead" (mockup 6). You decide; nothing links by itself.
If linked automatically: quicker, but a link is made without you seeing it, against your Q3 and Q4 rulings.

6. How long a phone or portal sign-in lasts (Q15)

Recommend: 30 days, renewed while in use, the same as the portal today.
If shorter (for example 8 hours): people ask for a WhatsApp code far more often, and each code is a WhatsApp message sent.

6Out of scope and risks

Not in this plan

  • Any new page: no Salesperson accounts page, no separate quick-create form, no new user management screen (your 00:45 note).
  • Sending any email automatically when a user is created or linked (your 00:50 ruling). Comes back only if you ask, and then as a box that starts unticked.
  • Creating users automatically, in bulk or at sign-in (Q3, Q4).
  • Switching off the old portal session for contacts you have not set up.
  • SMS codes. Only if a salesperson cannot receive WhatsApp.
  • CRM permissions for salespeople (Q8). Later a role change, no code.
  • Rewriting the older "who did this" fields across every module; #1281 decides that.

Risks

  • An email-only user cannot sign in until you press Send invitation email. That is your ruling working; their Sign-in part says "Invitation not sent" so it is not forgotten.
  • Only people you set up get the one sign-in. The rest stay portal-only and are recorded against their WhatsApp contact until you set them up; the User column on Internal Users shows who is left.
  • WhatsApp code message. If the approved code message is paused, phone codes stop; email and password still work. If its wording names the portal, you will be asked before S1 whether it can be used for the sign-in page too.
  • No background worker, no codes, as already true for the portal.
  • Admins signing in by code is weaker than a password if a SIM is stolen; you accepted it.
  • A changed WhatsApp number blocks that person's phone sign-in until you confirm the new number (mockup 13).
