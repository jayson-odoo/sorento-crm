7. How it reads the data (no new write paths)

One read endpoint: GET /api/v1/audit/history/{entity_type}/{entity_id}, with event, user, line and date filters. It returns entries already merged and in plain words. Each entity type has one reader entry, which grows one wave at a time. That entry says which trails to merge:

  • Every record: its audit_logs rows, plus its child rows (root_entity, as the AuditTrail already does).
  • Order inquiry: also the batch rows whose row_ids include its rows, the decision trail, reserve events, the OI rows' Now/Before, and link events.
  • Sales order: reuses planning_history_service, which already merges these trails for the SO drawer.

Permission: the record's own view permission (owner Q2). Before any trail is read, the record's company is checked, and a mismatch is refused (fail closed), as _authorize_po_history does (audit_logs.py:101-118). admin_listing_company_filter alone is not used, because it shows rows that have no company. Another company's ids are redacted, as #2295 does. IP and raw values go to admins only.

The one write-side change (owner Q3 "yes"): the two existing Confirm and Unconfirm log_audit calls also pass root_entity_type = the OI and root_entity_id = the OI's id. Nothing else writes.
