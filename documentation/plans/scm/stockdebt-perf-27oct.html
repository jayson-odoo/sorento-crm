Recommendation

Build A, then B, then C, with E's timing line in the first PR. A is the biggest win for the smallest change and does not alter what the board computes, only which products it bothers with. Park the cache (F) and only build it if A to C leave the warm p95 above 1.5 s; skip a worker-refreshed snapshot (stale by design).

How we prove nothing changes

  • Side-by-side check. A script builds the full board (every row, every month, totals, suppliers, counts, a sample of cell drills, the export rows) under 12 filter combinations, once on today's code and once on the new code, against the same database copy. The two must match exactly, number for number. The PR states the counts only.
  • Tests first. Each PR opens with a failing test that pins the speed property (for A: a product with stock but no orders is never computed), then the fix. The existing Stock Debt test suites stay unchanged and green.

How we measure

  • Locally: 10 requests per version on the prod copy, median and p95, same day. Target warm p95 under 1.5 s, cold under 3 s, no more queries than today (53).
  • Prod: after a release, the owner reads the new timing line in the backend logs. Crew never touches prod.
