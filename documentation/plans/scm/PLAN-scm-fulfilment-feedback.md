- **Incoming PL is a reference and can disagree with SPO** when a packing list has been converted; the popover names the shipment so the reader can tell.
- **History = SO booked, not delivered.** `consumption_v` covers 7 months and misses June. Label says "ordered".
- **Pool on hand drops ~30% of stock from the ask** (BRW 1,306,019 total vs 892,276 pool). Intended; group figure visible.
- **PI revision matching is a suggestion, not a rule.** The pre-load list carries no PI number, so the dialog proposes and the user confirms; a wrong "new" instead of "revision" is fixable by linking afterwards (a "Mark as revision of" action on the detail).
- **Public link exposes item codes and quantities to whoever holds the URL.** 30-day expiry, one token per send, revoked when the notice is resent; no prices on the page.
- **F7 depends on part 2 I merging first.** If I slips, F7 waits; nothing else does.
- **Changing the 40HQ seed** changes capacity for every future loading plan and PI fit; existing plans keep their stored `container_cbm`.

One source (the SO book, as retail), the SO required date, the same Plan-until cutoff; a line whose inquiry row is linked to a PO / SPO is netted by the linked qty, so no double count. No new label on screen. Form-only inquiry rows: none exist; a one-line add if one ever appears. Two consequences of the one source, from the build: the `include_lines` list carries project lines again (so `sum(lines) == open_so_need`, as before R1), and "Open SOs" counts the orders behind both channels, because that count drills into that list.
- **R16 (captain, 27 Aug) Supplier item codes bind through a deterministic ladder, and the answer is remembered.** Measured on the uploaded JINBAICHUAN list: 79 codes unbound by exact match; token reorder finds 4 (`SRTWC8357-RL-300` = `SRTWC8357-300-RL`); dropping a trailing trap size finds 28 but 16 of them are WRONG (`CWC7606-SH-180` is not `CWC7606-SH`, the 250), so the size rung binds only when the base product's description carries that size (`S-TRAP 250MM`). Ladder, first unique hit wins: 0 remembered alias for this supplier; 1 exact; 2 separator-normalised (`entity_resolver._norm_sql`); 3 token-set reorder; 4 size drop confirmed by description; else unmatched. Every auto bind and every human "Match to product" pick is written to `scm.supplier_product_code_alias (supplier_id, supplier_code, product_id, source)` and consulted first next time. Applies to the stock list and the PI reader alike (one helper). Forget drops the recorded answer only; the ladder answers again on the spot, so a code the ladder can resolve stays bound (without a badge) and only a code the ladder cannot resolve reads Not in catalogue. F11, slot B.
- **R17 (captain, 27 Aug) One code-matching format, and "none of ours" is an answer.** The loading plan's unmatched-code queue is the same shape as the delivery-schedule reconciliation list: a grid, the product picked INLINE per row (server-searched `SearchableSelect`), no "Match to product" dialog - a dialog per code turns twenty codes into forty clicks and hides the list being worked down. Beside it, Dismiss: some codes are the supplier's own accessory or spare and are never going to be ours, and a queue holding lines that can never be crossed off is one people stop reading. A dismissal is an alias row with NO product and `source = 'dismissed'` (migration 432 makes `product_id` nullable and pins `(source = 'dismissed') = (product_id IS NULL)`); it UNBINDS the stock rows and PI lines already carrying the code, rung 0 of the ladder reads it and refuses the code on every later upload, and Forget - the DELETE that already exists - puts the code back in the queue with the ladder free to answer it again. No confirmation dialog on Dismiss: it deletes nothing and detaches nothing. The PI detail keeps `MatchToProductDialog` for its Matched cell, where one code is being corrected rather than a queue worked through. F11, AC-F11.1 to AC-F11.6.
- **R18 (captain, 27 Aug) Refresh matching re-runs the ladder over what is still unbound.** Master data moves after a file lands - a product created, an alias recorded from the invoice screen - and the rows uploaded before it sit unbound under a code the ladder can now answer; the only way to make them catch up was to upload the same file again, which is a ceremony rather than a decision. One button, on the queue's header and on the loading-plan toolbar (the queue hides itself when it is empty, which is exactly the state somebody is working towards). It walks the SAME ladder the upload walks, over the supplier's UNBOUND stock rows and the lines of their current, un-converted proforma invoices only: a bound row is left alone (re-deriving a settled binding is a chance to disagree with it), rung 0 keeps a dismissal dismissed and a person's own pick ahead of every derivation, and what it works out is written down as an `auto` alias exactly as an upload writes it. `POST /supplier-code-aliases/rematch` answers `{inventory_bound, invoice_lines_bound, still_unmatched}` and the toast says so. F11, AC-F11.7.
- **R19 (captain, 27 Aug) A set's figures are its DRIVER member's.** Supplier codes like `CWC605-RL-180` name our product SET `CWC605-RL` (pedestal `CWCX605-RL` + cistern `CWCY605`), and no product carries the set code, so the ladder could never bind it. The supplier sells the whole WC; we book SOs on the members (2,308 open lines sit on set members). Every figure a set row shows on the loading plan (Need, Project / Retail, On hand, SPO, Incoming PL, PO, Earliest need-by, peaks, SO drills) is read from ONE member, the driver: the member that belongs to the fewest sets (ties: the lowest `sort_order`, then product code), which on this catalogue is always the pedestal. Shared parts are ignored on purpose: `CWCY605` sits in six sets, so a min-across-members would understate every one of them and a sum would count the cistern six times. Rejected: min of members; sum of members.
- **R20 (captain, 27 Aug) A set code binds only when it is spelled as the set is; a size suffix never auto-binds a set.** The ladder gains rungs against `product_sets.set_code` AFTER the four product rungs: 5 exact, 6 separator-normalised, 7 token-set reorder. There is NO size-drop rung for sets (`CWC605-RL-180` stays unmatched; `CWCX605-S-200` shows the supplier's size is sometimes a real variant of ours and sometimes not, and a set carries no description to confirm it against). A person matches those inline, choosing a set from the same picker (products and sets in one list, sets badged), and the alias remembers it. Company scope stands: a Sorento supplier list naming Mocha codes (`MWC...`) cannot bind under Sorento, set or product.
- **R21 (captain, 27 Aug) A set line explodes into member lines when a PI becomes a packing list.** `inbound_shipment_lines.product_id` is NOT NULL and stock lives on members, so `convert_to_draft_shipment` writes one inbound line per member, `qty x member.quantity`, each carrying the PI line as its source; the supplier notice, the PI and the PI detail keep the set code (that is what the supplier reads). Rejected: a set-aware inventory model (own module, not this lane).
- **R22 (captain, 27 Aug) Planning a container is ONE decision, so it is ONE button.** The loading plan toolbar carried a supplier picker, a date input and three outline buttons side by side, which made one errand read as four unrelated ones and gave the rare actions the same weight as the routine one. It becomes a single primary blue CTA, "Upload", opening a popup that owns the whole decision: supplier (server-searched `SearchableSelect`, required), plan until (optional, clearable) and which document is being sent (Stock list or Proforma invoice), then Continue straight into the EXISTING upload dialog for that document in fixed-supplier mode - neither upload flow is reimplemented - or "Plan without a file" for a supplier whose document is already on file. What was chosen reads back on the page as read-only text (Supplier, Plan until), never as inputs, and the occasional actions move behind a gear menu: View uploaded list (only with an attachment), Refresh matching (the same rematch the queue panel runs, R18), Change supplier / plan until. FE only: no endpoint, payload or query key changes.
