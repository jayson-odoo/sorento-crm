## 0. The linkage mechanisms that exist (what "SO line -> goods" can be derived from)

M1. OI placement links: `OIL.po_line_id` OR `OIL.spo_allocation_id` (OR `reserve_request_row_id` / `claim_id`), hung off OIR (`OIR.so_line_id` -> PSL -> `PSL.core_sales_order_line_id` -> SOL). Quantity = `OIL.qty`. A cancelled OIR (`state == INQUIRY_CANCELLED`) holds nothing, in every reader I saw that filters. Written by purchasing (cascade / manual) and by Ladder step 3 (`PSS._place_supply_borrows` 7642).
M2. AutoCount book SO linkage (text): `purchase_order_lines.from_so_line_ref` and `spo_allocations.from_so_line_ref` = `{db}:{DocKey}:{DtlKey}`; the SO line side is `sales_order_lines.source_ref`. Resolved to a sales ORDER at document level via `sales_orders.source_ref` (first two segments): `app/services/scm/order_link_service.py:687 book_so_numbers_by_ref`, `:740 book_sales_orders_by_ref`. Line level is a plain text equality `refs[event.key] == line.source_ref`.
M3. `scm.order_link_claim` (model `OrderLinkClaim`): SO number + item code pairing resolved to `so_line_id` + (`po_line_id` | `spo_allocation_id`). Written by ingest + `app/services/scm/supply_claim.py` (G12 born-claimed) + manual. Readers in my scope: `app/services/scm/project_bin_lock.py:46-135` (is a project-bin PO/SPO line claimed at all), `order_link_service.reservations_by_target/_claim_rows`, `project_order_inquiry_service.py:10102,11386`. UNVERIFIED which of these feed any supply number (project_bin_lock only gates the auto cascade).
M4. Retail CRM-raised SPO: JSON in the CRM SPO line's `purchase_order_lines.source_ref` (`so_coverage` ticks + `pulls`), written by `app/services/scm/spo_conversion_service.py` (`_spo_so_coverage_rows` 786, `coverage_for_so_lines` 892). SPO side then reached through `spo_allocations.po_line_id` (this FK is only set for CRM-minted SPOs; AutoCount SPOs have `po_line_id` NULL).
M5. AutoCount PO -> SPO transfer (the one in the brief): `SPO.from_po_number` + `SPO.from_po_line_ref` (text) point at `purchase_orders.po_number` + `purchase_order_lines.source_ref`. After transfer `PO.qty_received` = transferred, `SPO.quantity_received` = landed.
M6. `projects.so_line_allocations` (SOLineAllocation, `app/models/project_so.py:1832`): NOT a document link. One row per decision component: (`so_line_id`, `source_type` in on_hand / brw / borrow / ... / `order`, `warehouse_id`, `qty`, `decision_id`, `confirmed_at`). It is a hold on STOCK AT A BIN. `source_type='order'` = the Buy leg (not a claim on stock). Writer: `PSS._write_allocations` 8813 (Ladder step 3 deliberately writes NONE, see 8904-8911, it writes an OIL instead). Readers: `PSS._hold_query` 9736 (the one predicate: confirmed_at not null, warehouse not null, source_type != order, decision null or ACTIVE), which feeds `PSS._free_stock/_hold_rows/_holds_by_project/held_stock_by_location`, SD `_holds` 1688-1830, and `reorder_run_service._project_supply_reduction_map` 1290ff (raw SQL, its own restatement of "non-order, active decision"; does not check confirmed_at). Also `planning_reset_service.py:59`, `projects/purge.py:161`, `coverage_service.py:815` (mention only).

How SO line -> PO line is decided is therefore different per reader: M1 (OI links), M2 (book text ref), M3 (claims), M4 (retail JSON), or "not at all, pile level by product x warehouse" (several readers).

## 6. Divergences, ranked

D1 (biggest). Two opposite verdicts on a transferred PO line with an OI placement.
 - Stock Debt S4/S5: the placement follows the PO line onto the SPO allocation(s) it became; open SPO => SPO hold (still incoming), landed SPO => on-hand hold at the SPO bin; only the un-transferred remainder holds on the PO.
 - OI (P10 `_received_documents_for` 3346; `planning_change_service._placed_links` 1550): a PO link is "received" the moment `qty_received >= qty_ordered`, and `qty_received` IS the transfer. So the same placement is "stock in hand for this line" in OI/planning change, but "still on the water" in Stock Debt. Only `po_lines_with_open_chained_spo` (OI:13450) patches this, and only inside the reserve-received flow.
 - Loading plan (R5) ignores PO links altogether; PO occupancy (I6) and SPO document detail (I5) each show only direct links.

D2. Three different PO -> SPO join keys (section 5). S5 is the strict one (po_number + btrim ref + product + company + visible). The R7 own-arrival family (P4/S6) joins on `from_po_line_ref == source_ref` only. `purchase_order_lines.source_ref` is documented as NOT unique (OI service 4030-4033: bare ordinals on hundreds of lines), so P4/S6 can pair an SPO chained from a different PO. UNVERIFIED on data; measurable with a query for (source_ref) multiplicity.

D3. Two different SO -> PO resolutions. S4 uses OI links (M1) keyed by the placement. S6/P4 use the book text (`POL.from_so_line_ref` = `SOL.source_ref`). S7 also uses the book text, but pins a still-unlanded PO/SPO to a line (view only). So the same SO line can be "covered" in Stock Debt by an OI link on PO A and a landed pin from PO B chosen by book text. `held_by_line` nets them (STOCK-DEBT-STALE-PIN) but only by quantity, not by document identity.

D4. "Landed" for a shipment is defined four ways: `InboundShipment.actual_arrival_date IS NULL` (spo_supply, used almost everywhere), `shipment_status NOT IN (fully_received, closed, received, completed, cancelled)` (SQL views `on_order_v`, reorder/dashboard/container request), `actual_arrival_date IS NULL AND shipment_status NOT IN ('fully_received','closed')` (container_request `PL_NOT_ARRIVED_SQL`), shipment-LINE `line_status = 'received'` (incoming_stock_service), plus a fifth in coverage_service:90. The code docstring in spo_supply.py:2-5 says "the view repeats them in SQL"; it does not repeat the shipment test.

D5. "Open PO line" is spelled at least seven ways: `open_po_line_clauses` (PSS:10067, status set + crm_spo exclusion), `open_po_balance` (PSS:10835, status active/partial, SPO_HISTORY_SOURCE and `SPO-%` exclusions, nets OIR.po_line_id placed), OI picker (active/partial unless manual), `po_ordered_v`/container_request/stock_status/coverage/location_stock (OPEN_PO_STATUSES, no crm_spo exclusion), `site_pool_supply.open_po_by_product` (no status test, no ordered>received), `project_bin_lock` (line_status only), `_supply_document_balance` PO branch. Only `_po_rows` excludes the `crm_spo` shipping leg.

D6. The Stock Debt VIEW and the board/ladder read ONE `assign()` with different switches (S11): PO dated `expected_date` vs `issue + lead`, `pin_only` documents, `fulfils` PO pins, `lendable`, book S/O pins, forced overdue constants. Intentional, but any PO->SPO fix has to be made once in `_holds` (shared) and then re-checked against `view=True` only code (`_book_so_holds`).

D7. `visible_line_clauses` (retired) is applied in S4/S5/I2/SPO listings but NOT in P1 (`_spo_rows`), P4, `site_pool_supply`, `group_netting`, `stock_status`. So a retired line that still has `quantity_received > 0`... is visible by design; a retired never-received line should have `line_status` closed (UNVERIFIED) and thus fail `open_incoming_clauses`, which is the only thing protecting P1.

D8. Retail path (M4) is a separate mechanism: CRM-minted SPO ticks `so_coverage` in a JSON column on `purchase_order_lines.source_ref`, reached from the SPO allocation via `spo_allocations.po_line_id` (NULL for AutoCount SPOs). Surfaces in SO detail (I8) and SPO detail (I5) only. No supply-quantity reader consumes it.
