# UAC - supplier documents, proforma invoice first (9 Sep 2026)

Plan: `PLAN-scm-supplier-documents-pi-first.md`. Status: APPROVED 9 Sep 2026 (plan Status line governs).

## Journey

**Actor:** Ms Tee (purchasing), desktop, a supplier's email open with one or two spreadsheets attached.
Three suppliers, three shapes, measured on the 9 Sep sample set:

| Supplier | What arrives | Shape |
| --- | --- | --- |
| Kailu | `KAILU形式发票(Sorento)260730.xlsx` + `Sorento装箱单（凯路）260730.xls` | PI (11 lines, prices, no packing) and packing list (12 rows, no prices) as two files; the packing list splits SRTSC14-GM 85 into 50 @ 50/ctn + 35 @ 35/ctn. Neither file names the other; both carry the same date. |
| Jinbaichuan | `Jinbaichuan_Invoice.xlsx` | One sheet: qty, cartons, NW, GW, CBM AND RMB unit price + amount (cols 17-18), plus BL, container, seal. Rows 9-11 are spares and a shared-container note (`补8355水箱盖`, `家豪拼柜41个盆`) with no price. |
| Jiexia | `发票 SORENTO-2026.7.26.xls` + `装箱单 SORENTO-2026.7.26.xls` | Two files, both sectioned per container (`箱号:WHSU6243088`), packing list carries lid and fitting rows absent from the PI. Both state `INVOICE NO.: 2026JXL0726`. |

1. She opens **Proforma Invoices** from the sidebar and presses **Upload**. She drops one or more files and picks the supplier once. Nothing else is asked up front.
2. Choosing files does nothing yet (the SCM two-step rule, `useTwoStepUpload`). She presses **Test**. The result shows each file as what it is: proforma invoice, packing list, or both in one. For a packing-list file it shows which invoice it attaches to, already chosen when the file states the invoice number or shares the invoice's date; she changes it only if that guess is wrong. A packing list with no invoice to attach to is refused with the reason, because she uploads when she holds both documents.
3. The Test result also names any column header the system could not place (e.g. `尺寸（mm）`). She maps it to a system field in place; Test re-runs for that file with the mapping and the mapping is kept for every later file.
4. She confirms. The invoice appears with **our** number `PI-2609-001` and the supplier's own reference beside it. **Lines** are the invoice document as sent. **Packing** is the packing list as sent, each row matched to an invoice line by product, with the packed quantity checked against the invoiced one.
5. A packing row the catalogue does not know (spares, customs samples, a shared-container note) reads Not in catalogue. She dismisses it once; the next upload from that supplier lands it dismissed without asking.
6. When Kailu's packing list arrives days after its invoice, she opens the invoice, sees **Packing** empty with an **Attach packing list** action, and uploads it there. Same dialog, invoice already chosen.
7. When a container is ready she selects the invoices going into it and presses **Convert to packing list**. The container, seal and BL the supplier's packing list named come across onto our packing list's header; a packing row is placed whole or not at all. One draft packing list whose lines are the supplier's packing rows as packed: Kailu's SRTSC14-GM is two lines (one carton of 50, one of 35), so the printed list reads like the supplier's. The Packing Lists page has no supplier-document upload of its own; a packing list is born by convert or by hand.
8. In **System Management → Import column mappings** she sees, per document type, every system field and the Chinese and English headers that resolve to it, and adds or removes one.

**Automatic, never asked:** our PI number (monthly running number, same rule engine as `PL-2609-001`); the supplier reference (from the document, blank when it states none); which invoice a packing list attaches to (invoice number, else date); product on every row (alias table, dismissals); roll-up cartons, CBM, NW, GW on the invoice line; allocated and received quantities apportioned across split lines; the source files filed on the invoice.

**Not in this lane:** the forwarder/attachment **Upload** on Packing Lists (n8n path, stays as is); manual Create Packing List; SPO planning off a packing list.

## A. Our PI number (S1)

- **AC-A1 [BE]** Given a company with no `proforma_invoice` numbering rule, when a PI is applied, then a rule `PI-{yy}{month:02d}-`, 3 digits, monthly reset, is created for that company in the same transaction and the PI's `pi_number` is `PI-2609-001` (September 2026 upload date), the next `PI-2609-002`, and October restarts at `-001`.
- **AC-A2 [BE]** Given the Kailu PI states `货单号 KL20260730`, when applied, then `supplier_ref = 'KL20260730'`; given the Jinbaichuan sheet states no invoice number, then `supplier_ref` is NULL and `pi_number` is still minted.
- **AC-A3 [BE]** Given a PI already exists for (company, supplier, supplier_ref), when the same file is applied again without `file_as_new`, then the existing PI is updated in place, keeps its `pi_number`, and no second number is drawn. A file stating no reference never updates in place (no key to match on): it is always created fresh, and a second apply of the same file creates a second PI (ruling 9 Sep, Phase 2; the earlier `supplier_ref_missing` refusal is retired).
- **AC-A4 [BE]** Migration: every existing `scm.proforma_invoice` row gets `supplier_ref = old pi_number` (the derived `PI-<stem>-<n>` names become NULL), then a new `pi_number` minted per company in `created_at` order with the month of `created_at`; the rule's `next_value` and `last_reset_key` end at the state after the newest row. `uq_scm_proforma_invoice_identity` becomes (company, supplier, supplier_ref) with NULLs distinct; a new unique index covers (company, pi_number).
- **AC-A5 [FE]** List: PI number column shows our number; a new **Supplier ref** column follows it (size 140, `truncate` + `title`); search matches either. Detail header: our number as the title, supplier ref as the first meta item, "no supplier reference" when blank.
- **AC-A6 [FE]** Running Numbers page lists the `proforma_invoice` rule like every other rule; editing the prefix there changes the next PI minted.
- **AC-A7 [T]** `tests/scm/test_proforma_invoice_numbering.py`: A1 (two in a month, one in the next), A2 (Kailu fixture ref, Jinbaichuan fixture NULL), A3 (re-upload same number, refusal without ref), A4 (backfill function over three seeded rows across two months, assert numbers and rule state).

## B. Supplier packing lines on the invoice (S2)

- **AC-B1 [BE]** New table `scm.proforma_invoice_packing_line`: `proforma_invoice_id`, `proforma_invoice_line_id` (nullable), `row_no`, `item_code`, `supplier_code`, `description`, `product_id` / `product_set_id` (nullable), `qty`, `cartons`, `pcs_per_carton`, `carton_length_cm`, `carton_width_cm`, `carton_height_cm`, `cbm_per_carton`, `cbm_total`, `net_weight` (per carton), `gross_weight` (per carton), `total_net_weight`, `total_gross_weight`, `material`, `container_no`, `remark`, `match_state IN ('matched','unmatched','dismissed')`, company scope, timestamps. One row per supplier packing-list row, verbatim.
- **AC-B2 [BE]** Given the Kailu PI + packing list uploaded together, when applied, then the PI has 11 lines and 12 packing rows; both SRTSC14-GM rows link to the one SRTSC14-GM line; the line's roll-up reads cartons 2, cbm_total 0.040774, net 19, gross 21.3; every other line has one packing row.
- **AC-B3 [BE]** Given the Jinbaichuan sheet (combined), when applied, then lines AND packing rows are written from the one read: 11 lines with RMB prices (SRTWC8366-RL-300 at 465, amount 46500), 11 packing rows; rows 9-11 (`补8355水箱盖`, `补7606-N盖板`, `家豪拼柜41个盆`) are packing rows AND lines with no price, `match_state = 'unmatched'`.
- **AC-B4 [BE]** Given the Jiexia pair, when applied, then two PIs (one per container block, as today) each hold their own packing rows; the lid row `8840 盖板 366 pcs / 60 ctns` is an unmatched packing row on WHSU6243088's PI and is not an invoice line.
- **AC-B5 [BE]** Packing-list attach resolution, in order: the file's stated invoice number equals a PI's `supplier_ref` for the supplier; else exactly one PI of the supplier shares the file's date; else the `attach_to` the dialog sends. None of the three → 409 `proforma_invoice_required` naming the supplier and date. A packing list attaching to a PI that already has packing rows replaces them (re-upload = correction), never appends.
- **AC-B6 [BE]** Packing row → line match is by resolved product (alias table, then the line's own product), never by code text; a row whose product is on no line of that PI stays unmatched with `unmatched_reason = 'not_on_invoice'`; a row whose code resolves to a `dismissed` alias lands `match_state = 'dismissed'` on apply without asking.
- **AC-B7 [BE]** Dismiss on a packing row calls the existing `supplier_code_alias_service.dismiss` and sets the row's `match_state`; undo within the pending window restores `unmatched`. `POST /scm/proforma-invoices/{id}/packing-lines/{row_id}/dismiss`, `DELETE .../dismiss` for the undo, both gated `scm.proforma_invoice.upload`.
- **AC-B8 [BE]** Roll-up: after any packing write, each PI line's `cartons`, `cbm_total`, `net_weight`, `gross_weight` = sums over its packing rows; `pcs_per_carton` and carton dims = the rows' shared value when all agree, else NULL. Lines with no packing row keep whatever the PI document stated.
- **AC-B9 [FE]** PI detail gains a **Packing** tab (`useUrlTab` key `packing`) between Lines and Revisions. Columns: Row, Supplier code, Product, Description, Qty, Ctns, Pcs/ctn, L×W×H, CBM/ctn, CBM, NW/ctn, GW/ctn, Total NW, Total GW, Container, Matched. ## D. Our packing list carries the supplier's carton split (S4)

Ruling A (captain, 9 Sep, screenshot of the printed list): the exported packing list must show two
rows of one product from one supplier when the supplier packed it that way. So the (shipment,
product, supplier) uniqueness on `inbound_shipment_lines` goes, and the per-line derived figures
that today stamp a PRODUCT total on every line are apportioned instead.

- **AC-D1 [BE]** Migration drops `uk_inbound_shipment_lines_ship_prod_sup` and creates the same three-column index non-unique. Downgrade merges duplicates back the way `374_shipment_line_supplier.py:118-131` already does (sum qty and cartons, keep the oldest line).
- **AC-D2 [BE]** Convert writes one shipment line per MATCHED packing row: `quantity_shipped` = row qty, `cartons_count`, `pcs_per_carton`, carton dims, `cbm` = row `cbm_total`, `net_weight_per_carton` / `gross_weight_per_carton`, `description` from the PI line, `remarks` from the row, `unit_cost` / `currency` from the PI line. Kailu → 12 lines; SRTSC14-GM twice (50 @ 50/ctn and 35 @ 35/ctn), both at 36 CNY. A PI line with no packing rows converts as today (one line per product per supplier, its own columns). `proforma_invoice_shipment_link` rows still one per PI line, `qty` = the sum placed.
- **AC-D2b [BE]** Placement is whole packing rows: `line_quantities` applies only to PI lines with no packing rows; a request naming a partial quantity on a line that has packing rows is refused 422 `packing_rows_place_whole`. A PI whose rows are all placed reads converted; rows can be left for a later convert only as whole rows (`packing_row_ids` in the request, default all unplaced).
- **AC-D2c [BE]** Header carry-over: when every selected PI's packing rows (else its header `container_ref`) name ONE container, the draft's `container_number`, `seal_number` and BL (`bill_of_lading_number`) are prefilled from them; when they name different containers the fields stay blank and the response carries `header_conflicts: ['container_number']` which the dialog shows as one line. Jiexia WHSU6243088's PI → draft with that container and seal WHA45....
- **AC-D3 [BE]** Dismissed and `not_on_invoice` packing rows never become shipment lines; their descriptions are appended to the shipment's `notes` as "Supplier packing list also lists: ..." so customs filler is not lost.
- **AC-D4 [BE]** `update_shipment`: two lines of one product from one supplier are legal. `_duplicate_line_product_id` and its 409 are removed. `_upsert_shipment_lines` claims by line id first; a payload line WITHOUT an id whose (product, supplier) matches more than one existing line is refused 409 `line_id_required` ("Product X is on two lines for this supplier; edit them by line"), never guessed. `_merge_shipment_lines` no longer runs on update. It still runs on the external n8n create route, whose payload has no carton grain (unchanged behaviour, one row per product).
- **AC-D4b [BE]** External n8n route (`/external/packing-lists/`) updating an EXISTING shipment that has source PIs (`proforma_invoice_shipment_link` rows): header fields only (container, seal, ETA, shipment date, dates), lines untouched, `lines_skipped_reason = 'lines_from_proforma_invoices'` in the response and the integration log. A shipment with no PI links keeps today's per-product line replacement. So the manual → n8n → back flow is unchanged for forwarder-born shipments and cannot flatten a converted draft's split.
- **AC-D5 [BE]** `refresh_shipment_line_statuses` apportions: the product's SPO-allocated total and received total are walked over that product's lines in (created_at, id) order, each line taking up to its `quantity_shipped`, the remainder flowing to the next, any overflow landing on the last. 50 + 35 shipped, 60 allocated → line A 50, line B 10.
