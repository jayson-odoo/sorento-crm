v3 recommendation: option (i), one CRM shell for everyone. I found no blocker. A salesperson you have set up as a user signs in like staff, through /signin or their WhatsApp link with the same code, and uses the CRM: the same sidebar, trimmed to what their role allows, and the same pages. Project sales and every simple form then have one screen each, the staff one. The portal's own form pages are retired kind by kind as each staff screen gains what the portal form does today. Two things must hold, and both are in the plan:

AHow it works, in 8 steps

Plain words first, file references after each step.

1
One way in, two doors to it
The salesperson either opens /signin and picks Phone (or Email), or taps a WhatsApp link from Sorento as today. Both ask for the same 6-digit WhatsApp code. (/signin phone mode is live: app/(auth)/signin/components/phone-signin.tsx; the WhatsApp link opens the portal verify card, PortalVerifyCard.tsx.)
2
The server decides who this is
The code proves the WhatsApp number. If that contact is linked to a user you created, the result is a normal CRM session, the same kind staff hold, marked "signed in by phone". If the contact has no user, the WhatsApp link opens today's portal, unchanged. Nobody gets a user automatically (your 27 Sep ruling). (Phone sign-in: app/services/phone_signin_service.py; one contact per user: uq_users_respond_contact_id, app/models/user.py:142-148.)
3
Where they land
Today a salesperson is sent to the portal home (home_path_for_user, phone_signin_service.py:294-326). Under one shell they land on the CRM home instead, on a "My work" page: their open requests, their projects, their target. A WhatsApp link that points at one request lands on that request's CRM page.
4
The same frame as staff
Every page sits in the same CRM layout (Demo1Layout, app/(protected)/layout.tsx:64): sidebar, search, notifications, user menu. The sidebar already hides every item the user has no permission for (lib/menu-access-filter.ts:11-37), so a salesperson sees only their items. There is no second frame and no second copy of any page.
5
What their session can reach: permissions
The salesperson role (it exists, alembic/versions/identity_0001_s0_model.py:47) is granted only the create, view and edit permissions of the modules they use. Every page checks the permission (RequireAccess), and every API route checks it again (require_permission, app/dependencies.py:414-450). A salesperson who types a staff URL by hand gets "Access denied" on the page and a 403 from the server.
6
What rows they see: "only theirs", enforced by the server
For each module a salesperson uses, their lists and record pages return only their own rows: projects they own or collaborate on, requests they submitted or that name them as the salesperson. Staff keep seeing everything, as today. A record id from someone else returns "not found". This is one backend rule applied to each module (section C lists the columns it uses per module), the same idea as Customer asks already uses (app/api/v1/sales/customer_asks.py:41-71).
7
Buttons: same page, fewer buttons
The salesperson's project page and quotation page are the staff pages. Buttons they may not use, such as Approve below-floor pricing or Approve a registration, are hidden by the same permission check the page already makes (useHasPermission), and the server refuses them anyway.
8
Everything they do is recorded as them
The audit log names the user and how they signed in (identity S0, shipped). No contact-versus-user split in the history.

How convergence guarantees one behaviour
  • Backend: each portal form's write already goes through the module's service, or partly so for the legacy forms (portal_service.py:1433, 1442 create stock inquiry and purchase request rows themselves). Under one shell the salesperson calls the staff route, so the portal-only write path stops being used by set-up users and is deleted with the portal form.
  • Frontend: the staff page is the only page. What the portal form did better (AI extract, resubmit after rejection, salesperson fixed to self) is added to the staff page, where staff gain it too.
  • Guard: the v2 route allowlist test still applies, flipped: no new route may be added under app/(auth)/portal/ at all. The portal only shrinks from here.

The one backend rule ("only theirs")

One shared function decides whether the caller is limited to their own rows: they hold the module's new *.view_own permission and not its view. When limited, the module's list and get-by-id queries add "submitted by me or naming me", using that module's columns from the table above, with "me" meaning the user id and their linked contact id. Today two modules already do this in their own way (tickets, tickets_service.py:68-76; customer asks), so the second and later modules justify one shared helper.

Tests for every module: a salesperson's list holds only their rows, and another salesperson's record id returns 404 on the detail route and on every child route (lines, attachments, comments, exports).

DWhat changes for salespeople, and what happens to the portal

What gets better

  • One place for everything: requests, projects, quotations, targets, customer asks.
  • After a project is approved, they can follow it, quote, issue and revise. Today it disappears from their view.
  • Same screens as the office, so staff can help by looking at exactly what the salesperson sees.
  • Notifications, tasks and search work for them as they do for staff.

What gets worse, honestly

  • The portal's single simple page is gone for them. A sidebar, a search box and a header take its place.
  • Staff screens carry more fields than portal forms. Fields a salesperson should not fill are locked or hidden per form (section C), but the forms are longer than the portal's.
  • On a phone, the sidebar sits behind a menu button: one more tap per page.
  • Staff wording ("Procurement", "Project Sales Admin") shows unless QB adds a salesperson heading.
  • Until a form converges (phase 4), its portal version stays the way they file that kind of request, so there are two places for a while.

What this tells us
  • Each simple form costs about 100 to 400 duplicated lines. That is tolerable, and they already work. Leave them alone.
  • The one rich flow already on both sides, sales opportunity, has been rebuilt line by line as a "mirror". Every change has to be made twice. This is exactly the cost you want to avoid.

3Current state: who sees what

Portal: "only theirs", enforced per route

  • Most forms require the row's contact_id and space_id to match the token's, otherwise 403 OWNER_MISMATCH or 404 (BE portal_service.py:853-854, 961-984).
  • Price tag checks the contact only (portal_price_tag.py:849).
  • Sales opportunity is scoped to every agent linked to the contact (BE app/services/sales/portal_agent.py:24-33).
  • Company scope is the contact's companies (BE app/services/company_scope_resolver.py:287-348).
  • Form visibility is per market segment plus per-contact overrides (BE portal_form_visibility_service.py).
  • No team or manager view on the portal.

Staff: whole routes by permission, rows by company

  • require_permission gates a whole route; admin and superadmin pass everything.
  • Rows are filtered by company only. Per-person row limits exist in just two places: tickets (tickets_service.py:68-76) and customer asks (app/api/v1/sales/customer_asks.py:41-71, own agent plus teams you lead).
  • Projects are readable by anyone with the view permission, on purpose: "Reading is intentionally wide open ... a read filter would defeat it" (BE app/services/project_service.py:407-408). Edits are limited to the owner, collaborators or managers (:410-419).
  • Opportunities have no per-person read limit either (BE app/api/v1/sales/opportunities.py:82-110).

Permission-aware UI today

  • The standard is "hidden, not disabled" (documentation/plans/PLAN-permission-gating.md:200, still marked draft). The sidebar hides what the effective user cannot open (documentation/plans/identity/PLAN-menu-perm-gate-06oct.md).
  • Helpers: useHasPermission / useHasAnyPermission (FE hooks/usePermissions.ts:33,41, used in about 376 files) and the page guard RequireAccess (FE app/components/common/RequireAccess.tsx:29-56).
  • No field-level permission mechanism exists. The only field-style slug, projects.projects.view_all_financials, is read in one notifier (project_notify_service.py:33).
  • The roles salesperson and portal_user exist (BE alembic/versions/identity_0001_s0_model.py:47-48). salesperson holds only sales.customer_asks.view and .edit (sat_0001_stock_ask_done.py:50-63).
The security fact every option has to handle If a salesperson is given the staff projects.projects.view permission so they can use the shared screens, they can read every project in their company today, including other salespeople's pursuits and customers. Building project sales once on the staff API therefore needs a new server-side read rule for the salesperson audience: own projects plus projects where they are a collaborator. It must be enforced in the backend, never only by hiding things in the UI.

7Recommendation and target shape

Option B, scoped to what it is for: features from project registration onward are built once. Nothing is migrated just to tidy up.

  • Front door unchanged. A salesperson still opens their WhatsApp link to /portal/c/{slug} and types the code. If you have set them up as a user, the code now gives a user session (S2, already designed in the 26 Sep plan, section 5.2). If not, nothing changes for them.
  • Portal frame, not the sidebar. A slim frame with the portal header and a short nav (Home, My projects). It reuses the portal's existing look. No sidebar, no company switcher. v2: the frame wraps the same staff routes; there are no portal project routes (section 10).
  • Feature screens built once. Project detail, quotation and later steps are written once as components that both shells mount (for example under components/project-sales/), against the staff /api/v1/project-sales API. Actions a salesperson may not take are hidden with the existing useHasPermission, and the backend refuses them anyway.
  • Only theirs, enforced in the backend. A new permission, for example projects.projects.view_own, which the salesperson role holds instead of view. Holders read only projects they own or collaborate on. This follows the pattern already shipped for customer asks (app/api/v1/sales/customer_asks.py:41-71). Staff with view keep today's wide-open reads.
  • Simple forms stay where they are. Stock inquiry, purchase request, sample request, new product application and price tag keep their portal screens and the token path. Contacts without a user use them exactly as today.

Why not A

Option A keeps the UI single but doubles everything behind it. The quotation flow alone has issue, approve, reject, revise, sign-link and export routes (app/api/v1/projects/quotation_documents.py), and its approval graph acts as a user. A contact-token copy of each, with its own owner check, is the duplication you want to avoid, moved one layer down. A is still the right pattern for the simple forms, which is roughly what sample request and new product application already do.

Why not C

C changes what portal users see, forces a user for every dealer contact, and makes every staff route a target. It costs the most migration and saves nothing B does not.

10v2: how "built once" is guaranteed

Your Q4 concern is the right one. The answer is structural rather than a matter of discipline: each screen has one file, at one URL, and the portal has nowhere to put a second copy.

The rule, in four lines

  1. One route tree. Every project-sales screen (project detail, quotation view and editor, revision, issue) lives only under app/(protected)/project-sales/**, the folder it already lives in. A salesperson opens /project-sales/<project>/quotation-documents/<doc>, the same URL staff open.
  2. Only the frame differs. app/(protected)/layout.tsx already wraps every staff page in one frame, Demo1Layout (app/(protected)/layout.tsx:64). It gains one choice: salesperson users get a slim PortalFrame instead. Everything inside the frame is the same component tree, rendered once.
  3. Permissions decide buttons, never the frame. Feature components ask "may this user issue?" (useHasPermission) and the backend answers the same question. No feature component may ask "am I in the portal?". That is enforced by a lint rule (below).
  4. The portal gains a link, not pages. The portal landing (app/(auth)/portal/c/[slug]/page.tsx) gets a "My projects" card that links into the shared routes. The simple forms stay exactly where they are.

12v2: what issuing and revising by salespeople needs decided (Q3)

Today's quotation rules, measured, then the decisions that letting salespeople issue and revise forces.

How issuing works today

  • Who may edit, revise and issue: anyone holding projects.projects.edit who can write the project: its owner, an approved collaborator, or a manager (BE app/api/v1/projects/quotation_documents.py:85-92, app/services/project_service.py:399-419). Quotations on an unapproved project are refused (409 project_not_approved, project registration plan R4). There is no separate "issue" permission.
  • Internal signature first: no issue without a Sorento signature on the document (project_quotation_document_service.py:530-536, "Sign this quotation before issuing it"). Any writer can sign, and the signatory name and phone are free text (:187-188, 966-975).
  • Price floor gate: each line is checked against price_floor_rules (product, category or system level, percent of list or absolute; a series price wins over the rules) (app/models/projects.py:1016, project_pricing_service.py:174). Any line below its floor blocks issue until someone holding projects.quotations.approve approves. That permission goes to Project Sales Manager and to roles holding projects.projects.manage (alembic/versions/330_quotation_approval_gate.py:18-22). A quotation with nothing below floor never enters approval. Issuing uses up the approval, so a later revision that dips below the floor needs a fresh one (project_quotation_approval_service.py:9-28).
  • No floor, no gate: a line with no rule reaching it has no floor (project_pricing_service.py:183-193, "most installs start with no rules at all"). Nobody has yet measured how many floor rules exist in the live data.
  • Self-approval is not blocked: approve checks only the permission (project_quotation_approval_service.py:424-461). A manager can approve their own quotation.
  • Revision: revise freezes the live version and opens the next with the lines carried over (project_quotation_service.py:371-396). Issuing stamps R{n}.
  • Customer sign link: any writer can create it (quotation_documents.py:605-612). The customer accepts or asks for changes on the public token page.
The consequence in one line Granting salespeople projects.projects.edit lets them issue and revise their own projects' quotations straight away, with no new code. The only check left between a salesperson and a customer is the price floor, and that check only exists where floor rules have been set up.
