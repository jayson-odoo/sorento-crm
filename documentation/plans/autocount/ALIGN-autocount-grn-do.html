1. The ask, in your words

"just got a list of API from the autocount ... think the useful one will be just GRN and DO for now, need to learn how we did for products, stock balance, CRM side need to have a pull from autocount button for verification, and also ingestion endpoint for automated push from shared service after pull is verified, this one for GRN and DO i think abit tricky cause it is by doc date, so meaning we need to loop by doc date to check? any design we can do to cater this ah? and the DO is abit tricky also cause yeah DO has a lot of field and we need to store pretty much everything there ya, including the branch name, also the reference to the sales order line also need to store, the GRN the reference to SPO/PO also need to store, but i think the API macam tak ada I am asking the vendor, basically we need to link the DO back to the SO and GRN back to the PO / SPO, the uploading of order tracking is still needed after the integration cause only the order tracking stores the transporter, actual delivery time and date, driver, lorry number etc i believe"
The short answer.
  • No looping by doc date on every run. JustNow every 10 minutes, a LastModified sweep of yesterday and today every night, and a cursor so an outage only replays the days it missed. Doc date is only for the one-off backfill and a "re-pull this day" button.
  • Same two steps as products and stock. A pull-for-verification screen in the CRM, then you switch the push on in the shared service. Same endpoint family and the same verdicts.
  • The DO lands on the delivery order you already have, the same row the tracking upload writes. Every field is kept, including the branch code and name, and each DO line links to its SO line.
  • The GRN lands on the GRN you already have, and each line links to its PO or SPO line.
  • The link depends on one vendor answer. AutoCount records "transferred from" on every line (FromDocType, FromDocNo, FromDocDtlKey). If the API returns those, the link is exact.
  • The tracking upload stays and owns transporter, driver, lorry, the actual delivery date and time, checker and trips.

4. Proposed sync: a cursor, not a doc-date loop

DoorWhenWhy it is enough
...JustNowevery 10 mincovers the last hour, so 50 minutes of overlap; a missed tick costs nothing
...byLastModifiednightly, from cursor - 1 day to todaycatches anything JustNow missed; after an outage, one call per missed day, not per document. The cursor moves only after a complete sweep.
...bydocdatebackfill once; manual one-day re-pull; deletion sweepthe only place doc dates are looped, and it is bounded

Edits after posting bump LastModified, so the whole document is re-sent and upserted by its keys; line ids survive. Cancelled is an update. Deleted documents cannot be seen by LastModified, so until the vendor offers a delete log, a nightly sweep compares the last 45 days of DocKeys by doc date and sends the missing ones to /deletions. Reruns are safe: the CRM answers unchanged to an identical or older push.

Before the push is on: the operator presses Pull from AutoCount on the Delivery Orders or GRN list, picks a date range (default yesterday), and sees the same review screen as products: Changes, an Excel view in the upload template's columns, Compare with my Excel, and a new headline, "N of M lines linked to a sales order line" (or "to a PO or SPO line").

7. DO and the order tracking upload: one delivery record

OwnerColumns on the same orders row
AutoCount pushDO number, date, customer, branch, delivery address, agent, Ref, remarks, money, cancelled, all lines and their SO links, provenance
Tracking uploadactual delivery date and time, transporter, driver, lorry plate, checker, trips, delivery days, KPI warning, delivered status
  • Matched on the DO number, in either order. Tracking first: the Master sheet creates the row and the push adopts it by number. DO first: the tracking row finds it as it does today.
  • Neither writer touches the other's columns; a test pins each list.
  • The DO detail (lines) upload retires once the push runs clean. The tracking upload stays.
  • Found while measuring: actual_delivery_date is declared as a date while the upload builds date + time; the time is kept in pickup_time. The plan confirms the live column type.

10. Open questions (my recommendation in bold)

  1. How do we store "pretty much everything"? (a) Typed columns for what the CRM uses, plus the full record in one JSON column. (b) A column for every API field. (a): nothing is lost, and there is no migration per new vendor field.
  2. Branch name: (a) the shared service looks it up and the DO stores code + name. (b) A CRM branch table. (a); a table waits for a screen that needs it.
  3. Where does the DO land? (a) The existing delivery order that the tracking upload writes. (b) A new table. (a): one delivery record.
  4. Where does the GRN land? (a) The existing GRN. (b) A new table. (a).
  5. Who holds the push switch? (a) The shared service, per entity and company, as for products. (b) A CRM flag. (a).
  6. Backfill start: (a) 1 Jan 2023, same as invoices. (b) Go-live only. (a): invoice lines point at DO lines.
  7. Retire the DO lines upload and the GRN lines upload? (a) Yes, after a week of push with the verification pull showing no differences. (b) Keep both.
  8. A tracking row for a DO not yet synced: (a) create it as today, and the push adopts it. (b) Refuse it. (a): tracking is never blocked by sync timing.
  9. Deletions with no vendor log: (a) a nightly sweep of the last 45 days. (b) Also a monthly sweep of older months. (c) Accept the gap. (a); add (b) only if an older deletion is ever found.
  10. A DO line whose SO line has not arrived: (a) land it unlinked, and the SO's push links it. (b) Hold the DO. (a).
  11. SO delivered quantity: (a) keep taking it from the SO push. (b) Recompute it from DOs. (a); (b) only if the two are measured apart.
  12. JustNow cadence: every 10 minutes.
