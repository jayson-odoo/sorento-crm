## Architecture decision

Keep existing ingress, span grounding, lookup/RAG and conversational context. For enabled staff contacts, supply the original objective and grounded candidates to one bounded reasoning loop. Let the model choose permitted capabilities, observe typed results and adapt. Do not reduce the objective to the current fixed intent enum or require a separate planner agent. Existing services remain the authority for calculations, valid transitions and writes.

The substantive addition is a durable task executor with a user-bound action boundary. Merely changing the model or increasing tool-call limits does not supply either. Reuse the existing assistant loop's provider, tracing and tool conversion code selectively; do not route console traffic wholesale into its shared integration-principal execution path.

## Components and contracts

1. Contact settings: extend app/models/access.py and user_management/contacts.py with independently patched agentic eligibility. ContactChatbotSection uses the existing service/hook layering. Default off, preserve existing AI replies gate, recheck before every side effect. Agent reasoning configuration is independent from the current contact parser override.
2. Console entry: retain current test turn endpoint behavior. Add a separately authorized real-task endpoint, proposed POST /system/chatbot/agent-tasks, accepting contact reference, workspace, message, client request ID and optional task ID. The server derives all identity; do not accept acting-user IDs or model-provided scope. GET task and POST task message/cancel must enforce the same access. Return accepted task ID and status; UI polling is observation only. No stored WhatsApp envelope prerequisite.
3. Actor boundary: resolve external contact ID within workspace to internal RespondContact PK, then User.respond_contact_id. Construct an immutable execution context containing operator, acting User, company context, contact and task. Re-resolve current grants on each operation/resume. Shared MCP API keys currently select an integration user and can broaden company scope; do not use them as authority for staff actions. Self-only console execution is the proposed first policy; delegation is unresolved.
4. Capability adapters: use explicit typed descriptors with input schema, read/write effects, required authority, preconditions, execution, reconciliation and result verification. Start with a small supported set, not automatic exposure of all HTTP endpoints or arbitrary SQL. Reuse current catalog metadata where accurate. Dispatch must enforce the currently enabled and permitted set, not every catalog entry. Discovery can refresh eligible tools when the task needs another capability.
5. Shared business boundary: routes and agent adapters must call the same guarded operation. If authorization currently lives only in a route, extract it with business checks into a shared entry point before exposing the action. Do not call form_action_registry handlers directly: optional permission metadata assumes the route already checked access. Preserve browser-equivalent grace explicitly, rather than accidentally choosing immediate execution via X-API-Key or Request=None.
6. Task persistence: proposed task record holds objective, actor bindings, status, revision, pending question, evidence references, model/prompt versions, limits and timestamps. Proposed action record holds unique operation ID, task step, canonical arguments, preconditions, claim state, attempt count, receipt, record IDs and verification result. Use atomic claims and lease fencing. Reuse existing worker/scheduler infrastructure with fresh DB sessions; do not introduce a new workflow platform without a concrete unmet requirement.
7. Execution states: queued, running, waiting_user, waiting_domain_action, reconciling, completed, failed, cancelled. A domain action may be committed while notification delivery is pending. Unknown outcome is not failed-before-write. Local mutation and receipt should share a transaction where possible. Otherwise persist intent first and reconcile by stable operation ID/business readback. Never replay a whole turn blindly after a write. Multi-step work is not one database transaction and has no blanket rollback.
8. Model integration: preserve native continuation blocks/signatures across tool turns using provider-aware messages. Current normalization drops this data; Anthropic reasoning effort is accepted but ignored, and the assistant loop does not pass effort. Add capability validation and explicit unsupported-setting errors. Separate model retries from action retries. Reuse prompt versioning, encrypted keys and tracing. Select exact Gemini/Claude candidates only after current official API verification and CRM-task evaluation; no vendor/version winner is assumed.
9. Completion: tools return typed succeeded/rejected/pending/failed/unknown results with saved references, state, errors and side-effect status. The runner verifies requested outcome against receipts/readback before marking complete. Store concise task facts and evidence references; conversation memory and private reasoning are not an action ledger.

## Verification and release gates

## Owner correction and context design follow-up

The owner indicates Workflow Forms is probably not used. Its presence in code does not establish adoption. Remove it as the proposed first proving slice; retain only as a surveyed future capability. Ground the first slice in actual domain forms and their existing staff flows.

Read the owner-pasted Gemini blueprint. Adopt its durable execution, server-enforced authority, typed tool results and provider continuation principles where applicable. Do not import its greenfield async database rewrite, mandatory OAuth exchange infrastructure, five-table schema, multi-agent topology or backend-first delivery order without repo-specific need. Model/version/benchmark/statistical claims remain unverified and are not selection evidence.

Context contract: retain an access-controlled conversation log, but assemble bounded context per model call: trusted task instructions; current user message and recent exact conversation; a task summary with constraints and unresolved decisions; exact relevant earlier excerpts retrieved as needed; grounded entities with provenance; fresh authorized CRM facts; current permitted tool schemas; and the active tool-call/result sequence with required provider continuation metadata. Keep action receipts, identities and permissions authoritative in server state, not a lossy summary. Compact older dialogue by token budget, preserve corrections and unresolved choices, and retrieve original turns when precision matters. Never silently truncate required fields or pending decisions. Conversation history is evidence of user intent, not evidence of current business state. Separate test/live, contacts, workspaces and task scopes; recheck current access before retrieval.
