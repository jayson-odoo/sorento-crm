# Sample `/api/v1/external/chat/turn` responses

Real bytes, not hand-written: each file is the endpoint's own `response_model=TurnResponse`
output, produced through `TestClient` against the blank Postgres test schema with the LANE's
I/O seams stubbed (`next_assignee`, `sla_create`) and nothing else. The n8n action executor
renders its expressions against these. Regenerated by
`tests/chatbot/test_generate_out_of_scope_samples.py`, skipped by default -
`WRITE_CHATBOT_SAMPLES=1 venv/bin/python -m pytest tests/chatbot/test_generate_out_of_scope_samples.py -q`
re-captures both files the same way whenever the contract changes again.

Ids: contact `437264483` is the dev contact and is real. Every user id is synthetic
(`100000001`).

**`quick_replies` (AC-507/D9): a non-empty comma-joined STRING, or `null` - never `""`,
never a list.** Measured against 61 live `sub-output` tail captures (c32698c1): 60
non-empty strings, 1 null, 0 empty strings. `null` is n8n's own empty case
(`compile-current-state.js` sets it null when the access-choice list is empty), which is
why every `send_message` action below carries `null` rather than `[]` when the lane offers
no choices - `sub-sendmsg`'s `quick_reply` input has never been handed a list, and a `[]`
placeholder reached it as a type error on a failed turn before this was pinned
("'quick_reply' expects a string but we got array"). `result_set` has no such history: it
is `variables.last_result_set`, whose own default (`compile-current-state.js`) is `[]`,
never `null` - so `result_set` stays `[]` in the empty case and `quick_replies` is `null`,
two different empty values for two different reasons, not a typo.

**Action order for the escalation (`out_of_scope`) lane: `send_message`,
`assign_conversation`, `add_comment`, `send_message`.** This is the live lane order
(`lanes/escalation.py::_assignment_actions`) and both samples below preserve it; it does
not change with this pin. `send_attachments` is a fifth action, appended AFTER the last
message, and only when the tail's reply carries an `attachments_src` (not applicable to
this lane, which seals none).

## `chat-turn-out_of_scope.dry-run.json`

A test-run envelope (`test_run_id` set). **All four actions, same order, same keys** as the
live turn (AC-507), and every action's `dry_run` is `true`. D14 / H37 still holds
underneath: no seam is reached, so no assignee is picked, no cursor moves and no SLA row is
written. What a seam would have returned is stood in for instead, so the executor can render
one set of expressions against both files:

* `assign_conversation.respond_user_id` is `null`, with `preview: true` beside it;
* `add_comment.mention_user_ids` is `[]`, `preview: true`, and the three SLA timestamps in
  its text read `<preview>`;
* both `send_message` texts are REAL - neither depends on a seam (one is fixed, the other
  interpolates the team the ladder resolved before any seam was reached);
* both `send_message.quick_replies` are `null` (the pin above) and `result_set` is `[]`.

`assign_conversation` is always present here even though a live run omits it when the contact
is already assigned: only the seam knows that, so a preview cannot honestly leave it out.
`session_patch` carries what the tail would have written. (The top-level `is_test` field
reads `false` on this lane today - a known gap in `_run_escalation_arm`'s own `TurnResult`,
tracked separately; every action's own `dry_run`, which is what the executor actually reads,
is correct.)

## `chat-turn-out_of_scope.assigned.json`

The same turn as a LIVE envelope: the lane runs its seams and every value is real. Use this
one to see what the executor actually receives in production.

Two things to read carefully:

* **`reply.text` is null.** The customer copy for this lane lives in the ACTIONS, not in
  `reply`: `escalate-catalog` composes the out-of-scope acknowledgement with
  `includeResponse: false`, so it is session bookkeeping rather than a message to send. An
  executor that sends `reply.text` when it is set, and the `send_message` actions always,
  is correct for every lane.
* **`send_message` carries `quick_replies` and `result_set`**, filled from the sealed reply
  after the tail runs. `quick_replies` is `null` and `result_set` is `[]` here because this
  lane offers no choices and returns no rows; both keys are always present, so the executor
  never has to test for a missing one. When the tail produces an `attachments_src`, a fifth
  action (`send_attachments`) is appended after both messages.
