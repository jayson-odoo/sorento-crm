2. Why the outstanding question stayed open from T5 to T9

The bot keeps one open question per contact in session_vars.open_question. Each turn, decide() reads the new message against it and picks one of four readings (answer, refine, new ask, carry). The picture shows which reading each turn got.

T5 arms the question. T6 cannot close it. T7 to T9 each "narrow" it, which re-arms it and replays its poisoned customer id.

Why "got eta" did not close it, in three plain facts

  1. A domain word only counts when an entity rides with it. The rule at turn/decide.py:459 checked is "domain in message and entities" gives NEW_ASK. "got eta" named incoming but no product, so it fell to the last line, CARRY nothing_answered (decide.py:497).
  2. "Not an answer" means "leave the question exactly as it was". Owner hand pass 3 ruled that an aside must not re-ask the open question, so apply files it as answer_pending_not_an_answer and keeps the pending, its status, its document axis and the carried customer (turn/apply.py:712-721 checked). The ruling was aimed at asides like "ok thanks", and it also swallows a real change of topic.
  3. Outstanding questions never expire. Only the three escalation offers have a three-turn timer. outstanding_scope / outstanding_detail are sticky on purpose (R22: "a TTL would close it behind a customer who is still reading it"), so the question from 25 Sep afternoon was still open the next morning (turn/pending.py:155-183 checked).

And once it survived T6, the T7 to T9 photos each looked like a refinement: an entity, no domain word of their own. decide.py:477-485 returns REFINE refines_standing_subject without comparing the parser's own domain (incoming) with the question's domain (order), and apply.py:486-487 then overwrites the domain with the question's. A refine re-arms the same question, so the chain repeats every photo.

What would prove it. The T6 trace shows decision: carry / nothing_answered and rule answer_pending_not_an_answer; the T7 trace shows decision: refine / refines_standing_subject, verdict domain_in_message: false, rules outstanding_refined and domain_locked_by_pick. Anything else disproves this chain (section 8, query B).

3. The product dump in T10, step by step

Input: a photo of one product, M210-GM, captioned "X5". Output: a false count, "Showing 0", and hundreds of codes across three messages.

  1. The caption is glued onto the code. The photo reader returns the code M210-GM and, separately, the caption "X5". The text handed to the parser is built as "{caption}: {codes}", giving X5: M210-GM. The quantity is now part of the product's name. app/services/media_extract/service.py:322-329 checked; format from 25d4d6aa3 (#1139, 23 Sep). Uncertain only whether the vision model itself read "X5:" into the raw; the stored media job's caption field settles it.
  2. The parser keeps it whole. The parser has one message-level demand_qty and no per-product quantity slot, and no prompt line saying a leading "xN" is a quantity. So the product raw is "X5: M210-GM". head/parser.py:127 checked
  3. The code matches nothing. Folding strips hyphens and spaces only, giving X5:M210GM. No product has that code. resolve_gate.py:53, :615-629; turn/state.py:27
  4. The "one-letter Mocha code" gap. A stock question asks the resolver for products that "have stock". That filter is withheld when the customer typed a real code, and "is it a code?" is decided by _CODE_SHAPED, which requires two leading letters and no colon. "X5: M210-GM" fails it, and so does every bare Mocha code like "M210-GM" (one letter, then digits). Both are treated as descriptive words, so the "has stock" filter goes out with no product words to narrow it. The resolver counts the whole in-stock catalogue: 5,857. lanes/business/gate.py:174-176 checked (since dbba826bf, #659), resolve_gate.py:594-612 checked and :769 checked
  5. The sweep is treated as a real answer. A positive qualifying_total counts as "the set was answered", so the catalogue rows are kept. The 16 Sep guard for exactly this symptom ("5,783 products have stock. Showing 5.") does not fire because the entities now carry real uuids. This is a recurrence through the one-letter gap. turn_runtime.py:1022-1025 (_without_guesses), :2510 (_answered_unfiltered)
  6. "Showing 0". The header builder appends "Showing N." whenever the total is larger than what was shown, and 0 is smaller than 5,857. The owner's ban on paging text is not written anywhere in the repo, so nothing stops it. lanes/business/answer.py:2573-2587 checked. Why the stock tool drew 0 rows is uncertain; the T10 tool args settle it.
  7. The uncapped miss line. For each company that returned nothing, one sentence names what was searched. That subject is built by joining every entity's code with no cap, so "*Mocha and Sorento:* no stock records found for product ..." listed hundreds of codes and WhatsApp split it into three messages. lanes/business/fetch.py:2519 checked calls _axis_labelled_subject (:1229 checked); from #659 and #700

5. F7 redone: how the photos were still slow and out of order with Ordering ON

Correction to the scout report. The scout inferred Ordering was off from the turn numbers. With the owner's fact that Ordering is on, that inference is wrong, and so is its consequence "3 of 4 photo turns' state writes were lost". Below is what Ordering actually guarantees, and why the symptoms still fit.

What Ordering does, in code

  1. Arrival. Each message that reaches /chat/turn takes a ticket for this contact (a Redis counter), before its row is inserted. Ticket order is arrival order at the CRM, not the order Samantha pressed send. engine.py:831, :847-871 checked; dispatch.py:201-226 checked
  2. Wait. The turn polls every 200 ms until every earlier ticket is done, for at most 45 s (chatbot_queue_wait_seconds). Past that it fails at stage queued and sends the generic error reply. engine.py:911-933 checked; dispatch.py:253-301 checked; config.py:145 checked
  3. Everything slow happens inside the slot. Media extraction, the state read, the turn number, the parser, resolve, fetch and compose all run in _run_stages, after the wait. So one photo holds the contact's slot for its whole extraction (up to 30 s of polling, sync_wait_seconds) plus the rest of the turn. engine.py:935, :1224, :1249, :1306 checked; media_access_service.py:77 checked
  4. Release. In a finally, the counter moves up to this ticket and the next waiter goes. engine.py:987-1009 checked

How the symptoms still happen with Ordering on

photo arrives ticket waits for own run (extract ≤30 s + parse/resolve/fetch) reply at P1 t=0 s 1 nothing ~20 s ~20 s P2 t~0 s 2 P1 (~20 s) ~15 s ~35 s P3 t~1 s 3 P1+P2 (~35 s) ~12 s ~47 s P4 t~1 s 4 P1+P2+P3 (~46 s) ~12 s ~58 s <- 45 s budget is 1 s away n8n HTTP node times out at 60 s

Illustrative numbers, shaped to the reported 20 to 58 s spread. Real times come from query C.

  1. Latency is a staircase, by design. Serialised turns add up: the fourth photo waits for the first three. The reported 20 to 58 s spread is exactly the shape serial processing gives. T10 at ~58 s was within ~2 s of n8n's 60 s HTTP timeout, and its queue wait was within a few seconds of the 45 s budget. n8n chat-turn node timeout 60 s: documentation/plans/chatbot/n8n-changes.md:35 checked
  2. "Out of order" is arrival order, not send order. Ordering answers in the order messages reached the CRM. respond.io sends one webhook per photo once that photo is uploaded, and n8n forwards each on its own; four photos sent together can reach the CRM in a different order than WhatsApp shows them. The replies then come back in CRM order, which looks scrambled to Samantha. inferred
  3. Turn numbers do not tell Ordering on from off. The turn number is count(*) of this contact's rows, read at the start of _run_stages, after the wait (turn_runtime.py:106-126, engine.py:1249 checked). With Ordering on, each photo counts every row inserted by the time its predecessor finished. Distinct numbers 99 to 103 therefore mean the photos arrived spread out enough that each row existed when the next turn counted; photos arriving within one second would instead share the highest number. Either way, numbers alone prove nothing about Ordering.
  4. No lost state updates. With Ordering on, each turn reads session_vars after its predecessor wrote them, so the scout's "3 of 4 state writes lost" did not happen. It also does not matter to the wrong answers: the poisoned open question (section 2) was stored before 26 Sep, and serial turns replay it identically.

The n8n dispatcher

Before S7, n8n's sorento-dispatcher popped one contact per second and serialised in front of the CRM. S7 step 3 deletes it (n8n-changes.md:1100-1114). If it is still in front, the CRM's ticket is always free and the serialisation happens in n8n instead; the symptoms above are the same. The live n8n workflow list settles whether it is still there.

What would prove or disprove "serialised, arrival order differs from send order"
  • Proves: in query C, each photo turn's first stage starts after the previous turn's finished_at (no overlap), ordered by created_at; and the respond.io message timestamps inside envelope are in a different order from created_at.
  • Disproves: overlapping windows with none of the three escapes in the logs, or created_at order equal to send order while replies still went out of order (then the reordering is downstream, in n8n or respond.io sending).

6. Owner rulings applied

Ruling 1: quantity comes from the parser, no regex

The scout's slice 5 proposed stripping ^[xX]\s*\d+ in code. That is withdrawn. What the parser has today, and what has to change:

  • Today: one message-level demand_qty (head/parser.py:127 checked); no quantity per product; no prompt rule about "xN".
  • Photo quantities never reach the parser: the vision step already returns them as attributes[kind=quantity], but only entity raws are put into the text the parser reads (media_extract/service.py:293-295). The caption is glued on as a prefix (:322-329).
  • Shape of the fix: the parser schema gets a quantity per entity, and the prompt tells it that a leading or trailing "xN" / "N pcs" is that product's quantity and not part of its code. The photo text is handed over so the parser can see caption and codes as separate things (for example on separate lines) instead of "X5: M210-GM", and per-line photo quantities go in as text the parser reads. Code only reads the parser's output.
  • Proof: replay the T5 and T7 to T10 captions through the parser and assert quantity and raw separately for each.
  • Not a quantity regex: the one-letter _CODE_SHAPED fix (section 3, step 4) is about code shape, not quantity, and still stands. Flagged here in case the owner reads it as the same kind of hard-coding.

Ruling 3: a real brand filter fed by the live brand list

  • Today: under the order domain a brand is fanned out to customer / customer_order / transporter (entity_resolver.py:126-136); the outstanding report takes no brand; the parser is fed no brand list (a search of app/services/chatbot/head/ finds none).
  • Shape of the fix: at turn time, read the live brands (the brands table; note two models map that table name, models/product.py:98 and models/projects.py:373, so the reader must pick one on purpose) and put them in the parser prompt; the parser emits a brand entity matched to that list; the resolver stops re-typing a brand as a customer; crm_outstanding_report and the other order reports accept a brand filter in the backend and in the MCP tool arguments.
  • Effect on this chat: T2 to T4 need no pick at all; the T4 label bug has no way to start.

Ruling 2: attachments were delivered

F6b and slice 10 are dropped. The T6 files arrived. The T10 missing file is still expected: the incoming rows on a stock answer come from the cross-domain ladder rung, whose attachments are deliberately not sent (D2, 12 Sep); packing lists on stock answers are #1247.
