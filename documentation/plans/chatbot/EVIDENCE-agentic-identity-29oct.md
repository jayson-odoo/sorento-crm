# Console-first agentic identity audit

Source: read-only snapshot `/private/tmp/sorento-agentic-discovery-20261028`, parent-pinned origin/main `3a097ebbea` (28 Oct). References below are relative to that snapshot. Discovery notebook read from the primary checkout: `documentation/plans/chatbot/DISCOVERY-agentic-crm-28oct.md`. No application edits, running services, DB tests, or external mutations performed. This is focused source tracing, not proof of production configuration.

## Settled owner requirements

Agent eligibility is toggleable per Respond contact. Its acting authority is the User linked to that contact, using existing RBAC, company/record constraints, and workflow/approver rules. First delivery surface is the chatbot console, with WhatsApp later. Understand ordinary semantic instructions and expose actual CRM operations, including form submission/approval/rejection. Operator delegation, confirmation policy, execution environment, notification treatment, and invalid-user behavior are not yet owner decisions.

## Findings

1. **The present console is a test harness, not delegated staff execution.** `sorento_crm_frontend/app/(protected)/system-management/chatbot-console/components/ChatbotConsole.tsx:478` selects the contact; `hooks/useChatbotConsole.ts:227` submits its Respond identifier with conversation state; `services/chatbotConsoleService.ts:55` uses apiFetch. Backend `sorento_crm_backend/app/api/v1/system/chatbot.py:96` defines `system.chat_history.view`; `:649-670` checks that permission but discards `_user` when invoking console_service. Selected contact identity does not authenticate as its linked User. `sorento_crm_frontend/lib/api.ts:21-42` separately propagates existing staff impersonation headers; contact selection is not that mechanism.

2. **Preserve the existing test path and clearly distinguish a new execution path.** `app/services/chatbot/console_service.py:119-159` borrows the latest real webhook envelope, failing if absent; `:181-216` builds a synthetic envelope with `is_test=True`; `:450-505` runs the engine in process. An internal staff agent should not require a previous WhatsApp turn merely to establish its identity. The console's blanket “zero writes outside turns” route/service comments are incomplete: `:535-540` documents real media quota/ledger/extraction-job effects; `:543-555` documents test-flagged shared-service idea writes, integration logs, possible storage upload, and real extraction-model spend. Thus even today's dry run is not a fully isolated sandbox. Do not switch `is_test` off and infer correct execution behavior.

3. **There are two different contact identifiers.** `app/models/user.py:74` links `User.respond_contact_id` to internal `respond_contacts.id`, with a non-null unique index at `:143-147`. Console requests carry `contact_respond_id` (Respond's external id); `console_service.py:160-163` looks up `respond_contacts.respond_io_id`. Resolve external contact plus workspace to the internal contact server-side, then its linked User; never join external id directly against `User.respond_contact_id`. Multi-workspace resolution deserves an explicit acceptance test.

4. **Current staff authentication is opaque-session based.** `app/dependencies.py:143-179` resolves the bearer token to a live session, reloads User/contact, and rejects non-ACTIVE users. `app/services/user_session_service.py:92-118` checks invalid/revoked/expired sessions and slides rolling sessions. `get_current_user` uses this at `dependencies.py:321-325`; older JWT docstrings are stale. The console operator's live session is the entry credential. An agent must not invent a session for the contact user or treat a model-supplied user id as authorization.

5. **Existing delegation/audit mechanisms are useful but narrower than the proposed product.** `app/api/v1/user_management/impersonation.py:50-117` restricts start to admin/superadmin and ACTIVE non-admin targets. `app/dependencies.py:182-237` requires the real admin plus a matching active impersonation session and stamps effective `user_id` separately from `real_user_id`; invalid/stale headers are ignored and revert to the real user. That fallback is unsuitable for an agent action intending to act as a specific contact: mismatch must fail closed. Company scoping also recognizes validated impersonation (`app/services/company_scope_resolver.py:175-186`). `app/audit_context.py:47-70` already models effective user, real user, contact, session, integration and tool fields. Contact-portal impersonation (`app/api/v1/user_management/contact_impersonation.py:1-9,55-62`) mints portal authority and is not equivalent to linked-User CRM RBAC. Reuse audit primitives and explicit delegation checks; do not silently equate either existing impersonation feature with permission to execute as any console-selected contact.

6. **MCP's transport principal is different from the required actor.** `sorento_crm_mcp/sorento_crm_mcp/http_client.py:48-56` creates its client with a shared X-API-Key. `app/services/integration_auth.py:47-115` resolves the integration key to `integrations.act_as_user_id`, rejecting missing/trashed principals; it does not resolve the selected contact's User. `app/dependencies.py:117-140` stamps integration attribution. Most importantly, `app/services/company_scope_resolver.py:244-248` grants API-key requests without contact_id+space_id all-company scope for compatibility; supplied contact identity instead uses contact-company grants (`:221-241`). Neither is linked-User company scope. Passing contact arguments to an existing MCP tool does not fix its acting User. Merely checking a permission slug before making that API-key call also does not reproduce record/company authorization.

7. **Authorization must cover reads as well as writes.** Staff `_scope_for_user` uses granted companies and active company (`company_scope_resolver.py:189-218`); router-level application stamps ORM scope (`:375-395`, mounted by `app/main.py:318-323`). `app/services/own_scope.py:59-68` derives the user's contact and sales agents; opportunity own-scope clauses are `:114-119`. `app/api/v1/sales/opportunities.py:46-84,247-287` applies own-record restrictions on reads and modifications. A tool discovery list filtered only by RBAC cannot replace those predicates. Agent-created sessions/background steps must establish scope explicitly; never inherit the console operator's or scheduler's scope.

8. **Contact chatbot grants are a separate policy system.** `app/services/chatbot/head/access.py:123-155` checks contact/space agent access and field-reveal keys, with hidden-spec policy. They are not UserPermissionService grants. `app/api/v1/user_management/contacts.py:480-491` is the partial chatbot-settings endpoint, protected by contacts.edit; `:526-527` saves chatbot_allowed. Reuse its partial-update pattern and ContactChatbotSection for the new toggle. Decide explicitly whether chatbot_allowed gates agentic entry and how existing reveal restrictions relate to staff-authorized reads. Owner's linked-User decision means contact agent grants cannot confer additional CRM authority.

9. **Existing form operations include meaningful authorization and side effects outside the service call.** `app/api/v1/procurement/purchase_requests.py:498-540` requires current revision, procurement.purchase_requests.approve, and assert_can_act_on_form before dispatch, then provides actor_user_id. Its contract explicitly includes notifications and approval automation (`:509-512`). Calling its domain method directly bypasses those route-level checks unless they are factored into a shared authorized boundary. Workflow forms already offer `app/services/workflow_forms_service.py:976-1007` allowed transitions and `:824-865` application against the submission's pinned version, current state and current user roles; application logs user_id and invokes notifications before commit. These are good semantic discovery/execution seams, not a reason to reimplement workflow rules in prompts.

10. **Deferred action reuse needs a deliberate channel and resume policy.** `app/services/form_action_dispatch.py:43-59` executes immediately for X-API-Key or no Request; browser requests may get a grace window and HTTP202 (`:61-71`). An agent routed through MCP would otherwise change the user's current undo/grace experience. `app/services/form_action_registry.py:66-70` explicitly assumes form routes already checked permission; the registry is not itself an authorization facade. `app/services/form_action_service.py:481-493` restores stored company scope and passes requested_by_id to the handler; it does not globally reload/recheck the requester's current RBAC. `:393-424` uses a conditional claim and treats domain 4xx stale-state failures as ineligible. Retain existing execution/cancel/undo machinery where applicable, but independently revalidate an agent's user, enablement, delegation, current scope and operation permission on resume. Do not represent 202 as a completed approval.

## Minimal reuse seams recommended

- Add an execution entry contract beside the existing dry-run console contract, with explicit mode and durable server-owned conversation/task identity. Resolve contact, linked effective User, operator and chosen authorized company on the server. Client `session_vars` and model tool arguments must not carry authority.
- Initially permit self-operation and reuse the existing admin delegation rules if that matches the chosen console journey; any broader operator delegation requires an explicit product decision. Operator access to the console alone is insufficient.
- Build small adapters around actual CRM operations. Preserve/refactor their route checks into shared application boundaries, then invoke existing business services. Reuse form registry handlers only after those checks. Avoid adding a universal action framework or exposing arbitrary DB/HTTP execution.
- Use the existing audit actor/source/correlation facilities plus task/action ids. Record the operator, effective User, selected internal contact, tool and result; propagate that identity to background work. Verify existing service-specific stamps do not overwrite the real operator.
- Derive discoverable capabilities from linked-User authority, and discover permitted records/current actions through scoped endpoints. Recheck at execution, after waits, and after contact-user relinking; binding a task to its initial User should prevent silent actor changes.
- Reuse the contact settings partial-save UX for default-off agent eligibility. Stop future actions after disablement; specify how an already-started or already-deferred action behaves rather than promising cancellation of committed work.

## Decisions for parent alignment

1. Can ordinary console operators act only as themselves, while admins use existing explicit delegation, or is a new delegation policy required? The acting User itself is settled.
2. Recommend blocking execution for missing/inactive/trashed linked User and no valid company, with no integration-principal fallback. Whether Q&A remains available is a separate product behavior.
3. Choose test-environment actual execution versus production execution, and whether existing notifications/automations are intended. Console-first does not mean WhatsApp side effects are absent.
4. Choose explicit confirmation/batch policy and deferred-action grace semantics. Natural-language understanding does not settle which high-impact actions require review.
5. Clarify company context for a user with multiple grants; preserve the system's scope rules and do not infer permission to combine every granted company.

## Focused verification contract for implementation

Use isolated PostgreSQL fixtures; no live business records. Verify external-to-internal contact mapping, cross-workspace collision, missing/relinked/disabled User, enabled/disabled contact, unauthorized operator delegation, self and valid admin cases, current-user/company/own-record restrictions for reads and writes, forged actor args, stale permission/company/approver/record state after wait, API-key principal mismatch, audit attribution, 202 pending versus committed results, retry/idempotency under concurrent submission, and notification behavior in the chosen environment. Preserve current dry-run semantics with explicit tests for known media/ideation exceptions. Browser journey must show actual effective identity/company/mode and verified business outcome, not only a successful model reply.
