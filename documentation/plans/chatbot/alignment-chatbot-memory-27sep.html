1. The ask, in your words

"I believe our chatbot plan includes things like episodes and even user profile. Because I think now we are using focus only to survive multiple turns. But I think we have episode as well and profile so that, like Claude, you got a user profile that is a memory that stores everything about that user, and also episode, for some context management so that it feels more human and conversational when you are talking with the chatbot. Because now our chatbot fails constantly in a human conversation: when things are asked out of the boundary the chatbot struggles to understand because it's a one-dimensional reply chatbot. So I think we need to look into that and I'm also interested to discuss how to implement this so that we can be an enterprise version of Claude Code."

And the constraint in the same issue:

"Token budget matters: the parser prompt is already ~22.8k tokens against a 200k tokens/min org limit."

What we found: the profile and episodes were promised on 15 Sep and were built, but they do almost nothing. Every conversation summary reads "Closed the stock topic.", nothing a dealer says is ever saved, and the one part that handles out-of-scope messages is the one part told nothing about who the dealer is. So most of this is a repair.

4. Open questions

  1. Q4.How much history rides on every message?
    Recommendation: the last 3 conversation summaries plus the dealer's last 3 messages in this conversation (at the levels that include them).
    If not: more lines cost more tokens on every message; fewer lines and "any update on that DO?" from two conversations ago is answered with "Which customer?".
  2. Q5.Delete the old double understanding pass ("why we delete?", answered in the PR comment of round 3)?
    Recommendation: yes, delete it and stop saving the search data only it uses.
    If not: each referring-back message of a contact with memory costs a second full pass (about 22.8k tokens and 2.6 seconds) to add one line that today says nothing.
  3. Q9.Who writes the graceful fallback?
    Recommendation: the AI writes only the opening sentence; every name, number and document comes from CRM data, and a guard swaps out an opening sentence that invents a number or a code.
    If not: the AI writes the whole reply: more natural, but it can invent a price or a date. Or it stays canned and robotic.
  4. Q12.Where do staff see the memory?
    Recommendation: the contact page's Chatbot tab, as the mockup in section 5 shows.
    If not: a separate page or tab: one more place to look.
  5. Q13.Who gets a handover?
    Recommendation: a commercial ask (discount, credit, price exception) goes to the dealer's own salesperson by name; everything else to the domain's team.
    If not: everything goes to the team, and the dealer's own salesperson may not hear about a discount request.
  6. Q14.The "enterprise Claude Code" direction: the bot doing things (quotes, complaints, orders)?
    Recommendation: its own ideation issue; this plan builds the memory half only.
    If not: it joins this plan, which then also carries a riskier class of change (the bot writing to the CRM).
  7. Q15.May a test console message save a test-only conversation?
    Recommendation: yes, a test-only conversation row, never a fact.
    If not: memory across conversations can be tested only in automated tests and your hand test, not on the console.
  8. Q16.Malay and Chinese?
    Recommendation: only the new memory lines get English, Malay and Chinese now; the opening sentence follows the dealer's language; translating the existing replies is its own lane.
    If not: this lane also translates every existing reply and report, and becomes much bigger.
  9. Q17.One lane or two?
    Recommendation: two: A = S0 to S3 plus your test, B = S4 after your verdict.
    If not: one lane: S4 ships before you have tested memory.
  10. Q18.Build the rarer pieces ("the usual", self-statements, "what did I ask") before measuring them?
    Recommendation: build them, and record today's counts as the baseline.
    If not: wait for evidence first; they stay missing until then.
  11. Q19.Which level does everyone get when you later switch memory on for all?
    Recommendation: Full memory, the level your test runs at.
    If not: at Past conversations nobody's profile reaches the bot unless staff give them Full memory, so "the usual" and the language preference stop working for them.

6. Out of scope and risks

Out of scope

  • The bot doing things in the CRM (quotes, complaints, orders): proposed as its own issue (Q14).
  • Translating existing replies and reports (Q16).
  • Memory shared between two contacts of the same dealer.
  • The bot messaging first ("I'll tell you when the ETA changes").
  • Switching memory on for everyone: your later decision after S3T.

Risks

  • Old memory misleads. Summaries never carry figures, the current message always wins, and your S3T test looks for exactly this.
  • A conversation that never ends (no topic switch): bounded by the 3-message cap, caught in S3T.
  • The understanding step regresses from the new instructions: checked against the existing test set before shipping.
  • Cost creep: an automatic test stops the fixed instructions from growing; the level caps what each contact adds.
  • Privacy: nothing new is collected; staff see and can delete every fact; deleting a contact deletes its memory.
