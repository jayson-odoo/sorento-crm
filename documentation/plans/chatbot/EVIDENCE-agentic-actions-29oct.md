# Agentic CRM: existing action inventory

Baseline **pinned** to extracted `origin/main` commit `3a097ebbea`, in `/private/tmp/sorento-agentic-discovery-20261028`. Investigated 29 October 2026. The ordinary checkout is older and was not treated as current application code. The existing discovery note at `documentation/plans/chatbot/DISCOVERY-agentic-crm-28oct.md` in that checkout was read as prior context.

This is a read-only source investigation, not a runtime verification or implementation plan. No application files, database rows, external services or user chats were changed. References below are relative to the pinned snapshot. Prefix `BE` = `sorento_crm_backend/app/`; `FE` = `sorento_crm_frontend/`; `MCP` = `sorento_crm_mcp/sorento_crm_mcp/`. Coverage is deliberately identified: representative journeys and route/service checks across the requested domains, not a claim that every body in the entire monorepo was audited.

## Main findings

1. **The business actions already exist.** The first agent experience can use actual submissions, approval/rejection, responses, ticket assignment and sales updates. It should call their existing guarded business paths, not invent a follow-up queue or reproduce their state changes with generic CRUD.
2. **“Form” names several different systems.** Domain submissions (complaint, stock inquiry, PR, sponsorship, new product application, etc.), versioned Workflow Forms, and the reusable Forms catalogue are not interchangeable. The catalogue's generic `FormSubmission` stores a status and JSON payload; it does not execute the PR/complaint lifecycle.
3. **Existing MCP is partial.** Four staff actions are already registered: complaint close, order cancel, PR approve and PR reject. There are also external IT-ticket creation and contact-scoped sales-opportunity logging tools. Most internal submission, attachment, transition and staff-management operations have no matching checked-in MCP catalog entry. A stronger model alone cannot execute them.
4. **Permissions are more than a module permission slug.** Existing routes/services combine action permission, company scope, own-record scope, revision currency, workflow roles, handling locks and state checks. For example, a ticket edit grant does not let any user move any ticket; service requires assignee/admin. Some old CRUD routes have only authenticated-user dependencies, so “expose all endpoints” would require a permission audit.
5. **A completed HTTP request is not always a completed business task.** Form actions may return 202 pending a grace window. Reorder planning returns 202 for a background run. PR approval commits the decision before best-effort notifications and automation; those later failures may only be logged. The console must distinguish saved draft, queued action, committed change and downstream outcome.

## Representative complete existing journeys

### A. Submit a PR/sponsorship form, then triage and decide it

**Existing user journey:** portal form → save incomplete draft → attach evidence → submit → staff opens PR/sponsorship detail → send for approval or reject submitted request → authorized approver approves/rejects pending request → CS processes/closes as applicable.

- FE draft, submit, revise and attachment clients: `FE/app/(auth)/portal/lib/portal-client.ts:556`, `:576`, `:629`, `:720`. UI is `FE/app/(auth)/portal/components/SubmissionForm.tsx`.
- `POST/PUT /api/v1/public/portal/submissions/{kind}[/{id}]` calls `PortalService.create_or_update_draft`; `POST .../{id}/submit` calls `submit_draft`: `BE/api/v1/public/portal.py:1216`, `:1228`, `:1252`.
- These are **portal-token/contact ownership** routes, not staff-RBAC routes. Kind must be allowed for the contact (`_check_kind`, `portal.py:816`); `PortalService.get_submission` scopes contact and space (`BE/services/portal_service.py:984`). The linked-user console cannot simply substitute an integration principal or bypass the token's business ownership rules. An internal actor adapter/reuse decision remains for planning.
- Discovery is already contact-aware: `/public/portal/me` returns visible form types (`portal.py:409`); `portal_form_visibility_service.py:1` describes base types + active market segments + per-contact overrides, with sales-agent linkage additionally required for agent-only kinds. These are **portal visibility controls**, not the requested agentic eligibility toggle and not a replacement for user RBAC.
- Save and submit intentionally differ. `PortalService.submit_draft` (`:1089`) permits draft/rejected states, handles resubmission, clears rejection state and moves stock inquiries into project-sales review. Sponsorship validates project requirements and usable line unit prices only on submit (`:1146` onward); PR-linked projects must be approved (`:1170` onward). Do not “fix” an incomplete draft by submitting it early.
- Attachments use multipart upload with existing record ownership, attachment-type quota/extension checks and configured storage, then link the resource (`BE/api/v1/public/portal.py:1542`). Binary upload is a distinct operation, not a file URL that the model can invent.
- Staff PR detail explicitly separates triage grant from approve grant: `FE/app/(protected)/procurement-management/purchase-requests/components/PurchaseRequestDetail.tsx:228`. Its service calls `set-pending-approval`, `reject-submitted`, and `approval-decision` (`.../services/purchaseRequestService.ts:275`, `:294`, `:322`).
- Routes: `BE/api/v1/procurement/purchase_requests.py:394` send-for-approval; `:444` reject submitted; `:497` approver decision. Each uses current-revision guard and `assert_can_act_on_form`. Triage requires `procurement.purchase_requests.send_for_approval`; final decision requires `.approve`.
- Handling-lock is conditional but real: if enabled and escalated, only lock holder can act, or admin while unclaimed (`BE/services/handling_lock_service.py:156`). Claiming itself requires escalation-team eligibility (`:220`).
- `PurchaseRequestService.set_pending_approval` (`BE/services/procurement_service.py:9799`) refuses a rejected request until salesperson resubmission; repeated pending calls avoid duplicate SLA events. `decide_approval` (`:10270`) rejects already-decided/nonpending requests. `_apply_approval_decision` (`:10332`) requires a nonblank rejection reason, commits status and attribution, notifies requester/contact, emits form-SLA event, then approval automation (`:10365`-`:10444`). Notification/automation exceptions are caught; full downstream delivery is not guaranteed by returning the updated record.
- **Existing MCP:** `crm_purchase_request_by_number` resolves a PR; `crm_purchase_request_approve/reject` call approval-decision (`MCP/catalog.py:1481`, `:1500`, `:1520`; `MCP/record_actions.py:146`). Fixed approved/rejected decision is inserted by handler. Missing catalogue capabilities: initial submission, draft/edit, attachment upload, triage, process/close, current revision and action eligibility discovery.
- **Contract mismatch:** reject MCP argument is optional, but service requires rejection reason. Tool description/schema needs to reflect the real requirement. Also, the examined in-system approve path checks `.approve` + state/lock/revision, **not equality to configured `approver_user_id`**. Do not claim designated-approver enforcement without additional evidence.

### B. Submit and act on a versioned Workflow Form

**Existing user journey:** published forms list → choose form → complete configured header and line groups → create submission → edit where its state permits → choose one currently allowed transition (possibly approval/rejection) → inspect updated submission/history.

- FE discovers published definitions and schemas without requiring definition-administration rights (`FE/app/(protected)/workflow-forms-management/services/workflowFormsService.ts:28`, `:37`). `WorkflowSubmissionEditor.tsx:168` creates a submission; `:395` saves it; `:400` renders allowed transitions.
- `GET /workflow-forms/definitions/published-for-submission` and `.../{id}/published-schema` require any runtime submission add/view or definition view grant (`BE/api/v1/workflow_forms/router.py:74`, `:81`, `:171`). This is a suitable existing discovery surface, distinct from the document Forms catalogue.
- `POST /workflow-forms/submissions`, `PATCH /submissions/{id}`, `GET /allowed-transitions`, and `POST /transition` map to `WorkflowFormsService`; action grants are submissions add/edit/view/transition (`router.py:249`, `:275`, `:304`, `:314`). Write routes use regular staff authentication, not API-key-capable dependencies.
- `create_submission` uses the published version, validates dynamic header and line group payloads and sets the schema's initial state (`BE/services/workflow_forms_service.py:714`). It is not a generic permissive “save any incomplete draft”: required-field validation runs on creation.
- Required fields, empty lists, numeric/date-range/email checks are at `:267`; line groups and unknown group validation at `:372`. These checked-in validators are light validation, not evidence of a complete conditional-field rules engine. No general Workflow Form binary upload contract was verified.
- Updates use the submission's frozen version, reject terminal state, and enforce configured edit roles (`:761`). Transitions also use that version, require an edge out of the current state and transition roles, log actor and remark, notify, then commit (`:824`). Original submitter receives state-change notification even without builder notification rules (`:895`).
- **MCP gap:** no matching workflow-form discovery/schema/submission/transition tools found in the static catalog. Calling a generic form submission route would bypass this workflow rather than implement it.

### C. Work a real IT-support ticket

**Existing user journey:** create draft → submit → assigned by existing team routing → assignee responds → assignee resolves → inspect history. Saving response text is separate from sending response and advancing state.

- FE service explicitly distinguishes save response, update-and-reply, submit draft and cancel draft: `FE/app/(protected)/ticket-management/tickets/services/ticketService.ts:116`, `:140`, `:153`, `:165`.
- `BE/api/v1/tickets/tickets.py:108` create; `:165` change status; `:182` submit draft; `:206` assign; `:222` save response; `:242` update-and-reply; `:261` save resolution; `:281` resolution-and-reply. Grants are `.add`, `.edit`, `.assign`, `.respond`, `.resolve` as appropriate.
- `tickets_service.change_status` verifies visibility, transition validity, and assignee/admin eligibility (`BE/services/tickets_service.py:667`). `submit_ticket_draft` requires actual draft state, uses IT-support round robin, stamps SLA deadlines, and records actor/event (`:1053`). The code raises on a nondraft ticket despite its docstring saying no-op: trust the body.
- **MCP partial:** `crm_it_support_ticket_create` calls the external endpoint (`MCP/catalog.py:1415`), not the complete staff lifecycle. Staff response/resolution/assignment/draft actions are gaps. External creator's attribution/permission contract needs its own audit before treating it as equivalent to linked-user staff execution.

## Execution semantics the parent plan must preserve

- **Action registry is not an authorization registry.** `BE/services/form_action_registry.py:32` models execute/capture/invert and tells-contact; its `permission` is optional (`:66`) because domain routes already enforce grants. Generic invocation of registered handlers would lose those checks. Reuse the guarded routes or an explicitly equivalent entry point.
- **Deferral is transport-sensitive.** `BE/services/form_action_dispatch.py:21` uses browser-session + configured grace to park an action and return 202 with `pending_action_id`, `commit_at`, `window_seconds`; `:46` treats X-API-Key or no Request as immediate. The agent must not accidentally skip the user's existing grace merely because execution goes through MCP. User's choice of confirmation/autonomy policy is still open; this finding does not decide it.
- **Pending is not success.** Existing `sla/form_actions.py:97` exposes current pending action, `:150` cancellation, `:170` undo, `:211` eligibility. `form_action_service.py:225` dispatches; `:323` sweep commits; `:544` cancellation is requester/admin gated. After commit, undo has distinct permission/eligibility and some actions have no inverse. “Undo” cannot mean unsending WhatsApp or reversing every side effect.
- **Carry company scope into delayed work.** `form_action_service.py:73` stores `__company_scope`; `_execute` (`:461`) restores it for delayed execution. The durable action cannot inherit whichever user's request happens to trigger a lazy commit.
- **Discover real action choices.** Workflow Forms already expose allowed transitions. Other domains have state-specific buttons and service guards. Neither RAG similarity nor natural-language confidence authorizes an unavailable action. They can resolve intent and entities; server checks remain authoritative.
- **Existing actor contracts differ.** Internal user, contact/space portal token, external integration act-as user, and agent-only sales scoping are separate. `crm_sales_opportunity_log` expressly requires contact+space (`MCP/catalog.py:891`), so it is not a generic internal staff action. Contact-to-user linking should select the authorized actor; it should not erase these domain rules.
- **Retry effects differ.** PR send-for-approval avoids duplicate pending events, but generic writes are not thereby idempotent. Pending approvals recheck state. Ticket submit raises after first success. A durable agent must reconcile actual state before retrying a lost response; each write's business semantics need validation, not blanket automatic retries.

## Coverage limits and conflicts to resolve

- No runtime/database/catalog-config inspection, API calls, browser clicks, tests or outbound notifications were performed. Tool absence means **no matching static catalog entry found** in `MCP/catalog.py`; `MCP/module_loader.py:93` can discover per-module `mcp/tools.json`, but no such checked-in files were found in this pinned tree. Runtime configuration can change availability.
- Complaints, stock-inquiry and many procurement/master-data operations received route-level inventory, not exhaustive branch review. Matrix identifies this explicitly. No claim that every existing system action is safe to expose now.
- Generic Forms submissions are plain `form_id/status/submission_data` (`BE/schemas/forms.py:158`, `BE/services/forms_service.py:289`). External `/external/forms` creates form **catalogue metadata**, ignores supplied sections/fields, and can send attachment notifications (`BE/api/v1/external/forms.py:25`). Neither is the business form submission journey.
- Governed discovery followed `PRINCIPLES.md` (simplest thing that works; journey → grill → UAC → plan). No UAC/implementation plan was authored here. The pinned snapshot lacks root `CLAUDE.md` and `CONTEXT-MAP.md`; parent should use the actual workspace copies explicitly as development guidance rather than pretend they came from the pinned commit.
- **Documentation conflict:** supplied older AGENTS text says deletion requires confirmation; pinned `documentation/reference/ADR-PRODUCT-STANDARDS.md:19` instead specifies server-deferred countdown+Cancel and no confirmation dialog. Flag for parent/user alignment before defining agent delete UX; do not silently overwrite either policy.

The most evidence-backed first demonstration is a real existing form journey with separate draft/save/submit and approve/reject operations, including a genuinely unauthorized or wrong-state request. Workflow Forms can prove dynamic-schema reasoning; PR/sponsorship can prove business side effects and revision/handling constraints. Parent/user should choose which real journey to put first, rather than imposing a synthetic sales follow-up workflow.
