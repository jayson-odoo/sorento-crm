How matching works today

  1. The catalogue is not in the prompt. Dev has 15,339 products; the parser sees none of them. It gets the spec registry instead (50 specs with every choice and its synonyms, about 2,400 tokens, cached) plus short lists of brands, product types and promotion kinds. One model call per message: 38,862 tokens in (38,656 cached), 440 out, $0.005 (prompt v94 lines 1767-1847; engine.py:4549).
  2. The parser extracts the words it found and what they are: product, category, brand, spec key and value (head/parser.py:139-197).
  3. Code checks each spec against the registry and drops what does not exist (head/grounding.py:594-749).
  4. Product names and codes are matched by code, not by the model: exact code, prefix, a small model call for a missed code, then similarity search over product names (entity_resolver.py:849 to :5767).
  5. The search filters products by type and spec values (product_spec_search.py:1103-1141, product_predicate_service.py:1072).

Is it the right way? Yes for names: 15k products are too many for a prompt, and similarity search in code is right. For specs it is right but incomplete: product type synonyms and class meanings ("jacuzzi = bathtub with massage jets") are the two parts of the registry the parser never sees, which is exactly where W05, W10 and W11 fail. Recommendation: show the whole registry, including those two, in the cached prompt and keep it live from the registry (today a registry edit reaches the parser only when a new prompt version is published). Cost about +$0.00005 per message, no added latency. Fetching candidates per message instead would cost about the same, add about 0.3 s, and add a way to miss.

Is the routing general?

The core is. The parser fills generic fields (message type, intent, domain, entities; head/parser.py:113-115); code picks the lane from those fields only (turn/apply.py:2076-2156, turn/route.py:65-109), and the tool is the domain's first tool (lanes/business/fetch.py:156-216). No product, brand or customer is named there.

But a layer of word rules sits in front of it. Past fixes added 30 places where code reads the message's own words (28 hard-coded, 2 from data). 8 of them rewrite the parser's domain or intent before routing, for example ranking words (engine.py:2674-2682), sales-order words (so_status.py:442-662), order-list words (order_list.py:38-110), dealer ETA words (engine.py:483) and Malay attribute words (predicate.py:115-139). Brand names are also typed into code in 3 places (gate.py:181, tier_gate.py:27, escalation_services.py:247). This is the scenario-shaped part. None of our fixes adds to it; NEW-1 and P2-F1 remove three of them. Proposal: retire the rest one at a time, each only when the parser gold set shows the parser already reads those messages right.

A. How today's bot answers a question

Is it ReAct? No. ReAct is a loop: the model thinks, calls a tool, reads the result, thinks again, and writes the answer. Today's bot is parser-routed: the model runs once, before any data is fetched, and only turns the message into structured fields. Code then picks the tool, fetches the data and fills a fixed reply. The model never sees the data and never picks the tool.

1. P1 Follow-ups lose context

What happens

On crew's parser gold set (real turns, TRAIN slice only), v1 reads 49 and 51 of the 81 follow-ups right in two runs; 29 fail in both. Giving the parser the whole raw chat did not help (59.9% vs 61.8% on all follow-ups), so the fix is not "more history". It is four specific gaps.

Why

  1. The current subject is cut on 77 of 81 follow-ups. It comes from the carried focus (session_state.py:23) through head/parser.py:809-848 and engine.py:4511-4522 into context.assemble. Since #1527 (9 Oct) the same block also carries the brand, product type, product detail and promotion lists (about 629 tokens, context.py:147-158), kept whole (:409-410), against a budget of 350 tokens (:29), so the shrink loop (:425-431) always drops the subject. The builder that the tests cover (parser.py:851-944) is no longer called, so no test saw it.
  2. An answered list still shows as owed. Lists are meant to stay open after a pick (the "sticky roster", PR #952, contract 36: _archive/chatbot/PLAN-chatbot-turn-rearch.md:116-121, AC-1522; extended in #1273), so "2 also" works. That part is right. But the parser's view of it says owed ["pick"] and "the assistant is waiting for a product_pick reply" even after the pick (question.py:73-93, #1247; context.py:400-402), so "the NEW one also" picks a list position again (TRAIN G070).
  3. Short replies that need the subject are read as chat (4 items: "office use copy", "what different", "why?", "purchasing"). Thanks and greetings are already right: "ok thanks boss", "terima kasih boss", "Hi" are casual in both runs (5 of 5). The rules that should catch the others exist (prompt lines 41-48, 321) but are starved of the subject (cause 1) and overridden by line 313 ("always classify from the current message's own content"), which contradicts lines 36-38.
  4. "Seat cover" read as a file request (4 TRAIN items). Not a missing rule: the rule against it exists, but (a) it sits in the find field near the END of the parser's output (head/parser.py:543), so the domain is already chosen (:113-114) before the model reaches it; (b) a catch-all line says a file type counts when "named OR IMPLIED" (prompt v94 lines 331-334, 391), and seat cover gets read as an implied installation guide; (c) the registry knows "seat cover" is the product type Toilet seat, but only the display name "Toilet seat" is shown to the parser (chatbot_parser_prompt.py:1293-1295, turn_runtime.py:740-743), so the only open slot left is the file type. "size?" fails because "size" is not one of the product domain's switch words (dev chatbot_domains).

A ranking needs period, how many, amount or quantity, delivered or ordered (lanes/business/report_ask.py:225-243; the 4 Oct ruling keeps all four as questions, no defaults, :8-9), and each is a separate turn (required_fields.py:315-318).   2. Answers are not read back: only the field just asked is taken (report_ask.py:183-212, :552-561), so "2026, top 10, by quantity delivered" answers one question and the rest are asked again; "3" is "not a number".   4. Shapes not covered: "how many dealers sell X" gets a top-10 list though the count exists (reports/ask.py:291); a dealer's brand filter is dropped silently (__init__.py:2026-2030). Plus a 10-per-10-minutes limit that counts every refine, and display issues (duplicate brand names, category codes, ISO dates, header not naming the sort).
